The shape of the work

Two systems, one governed path

The scope is not “all of AEM.” It is the set of features that control the path from a Workfront project and its approved asset to governed, searchable, reusable content in AEM Assets.

Source system

Workfront

Projects, custom forms, documents, approvals, and production context.

↓ Native connector · metadata mapping + linked folders
Governed destination

AEM Assets

Repository, metadata, tags, processing, search, permissions, reuse, and lifecycle.

The design principle

Workfront manages the work and production context. AEM Assets manages the governed asset and its reusable content context.

Adobe describes the native integration as a direct connection between Workfront and AEM Assets as a Cloud Service, supporting asset delivery, linked folders, and metadata mapping. Treat it as exactly that — not as a complete bidirectional synchronization platform by default.

What's in scope

The features involved

The capabilities split into three groups: AEM Assets (the governed destination), Workfront (the production source), and the integration layer between them. Two boundaries matter most as you learn: metadata schemas and profiles are different controls, and AEM as a Cloud Service processes assets through asset microservices and processing profiles rather than treating legacy workflow behavior as the default.

The destination

AEM Assets — the features you need to understand

Six capabilities carry the governance model. Learn what each one answers, and where its boundary sits against the others.

A · Folders

Governance, not the entire information architecture

Where is the asset stored?

Folders are the right tool for governance boundaries, access control, processing profiles, project or campaign organization, and controlled navigation. They are the wrong tool for answering every search question — a user may need an asset by brand, market, language, channel, campaign, rights status, or expiry date even when those attributes don't belong in the folder path. Adobe recommends a stable structure, because folder changes ripple into automation and processing configuration, and explicitly distinguishes folder-based organization from metadata- and tag-based discovery.

What you should be able to decide

  • What belongs in the folder path
  • Which folders are administrator-controlled
  • Which folders are linked to Workfront projects
  • Which folders need different permissions
  • Which folders need different processing profiles
  • How deep the structure can get before navigation breaks

B · Metadata schemas & forms

The business information model

What is the asset, who is it for, where may it be used, and when does it expire?

A metadata schema defines the fields shown on an asset — brand, campaign, asset type, market, language, channel, approval status, rights status, rights expiry, owner, reuse eligibility. The distinction that trips people up is that four different controls are involved:

Control

Metadata schema / form

Defines the fields available on an asset.

Control

Metadata profile

Applies default values based on the upload folder.

Control

Folder metadata schema

Defines properties of the folder itself.

Control

Tags

Controlled classification terms used for discovery.

Example · folder “Campaign 2026”

A profile sets defaults →
Business unit = Brand Marketing
Default region = Global
Lifecycle = Draft
Asset owner = Campaign Operations
The schema then asks the contributor for →
Campaign name · Asset type · Channel · Language · Rights status · Rights expiry

Your design responsibility

Challenge any field that is not searchable, not used by a workflow, not required for rights or compliance, duplicated elsewhere, or too hard for contributors to complete accurately. A good field has a clear purpose, owner, allowed values, and lifecycle.

C · Tags & taxonomy

Controlled classification

How should this asset be classified for discovery?

Use tags for controlled concepts — product category, audience, content theme, region, industry, campaign type, brand hierarchy. Do not let tags become a second, uncontrolled metadata system. Define who creates and maintains tags, which terms are allowed, whether synonyms are supported, how obsolete tags are retired, which tags are mandatory, and whether users may create their own. AEM supports tagging as part of asset organization and discovery, including AI-assisted tagging in the applicable Assets offerings.

D · Collections

Reuse views without duplicating assets

Which assets do I want to use together right now?

A collection is a set of references, not a second physical copy, and it can pull assets from different folders. That is what makes it the reuse primitive: an asset stays in its governed folder and also appears in a campaign or channel collection. A “2026 Summer Campaign” collection could reference assets stored across brand, product, regional, legal-approved, and localized-content folders at once.

The governance split

Folders for stable governance and access. Metadata and tags for discovery. Collections for temporary or collaborative reuse views.

E · Search & facets

The proof that the model works

Can a user find the right approved asset without knowing where it is stored?

Understand full-text search, metadata filters, tag filters, facets, saved searches, date and expiry filters, status filters, and contextual or similarity search where it's licensed. The most useful enablement exercise is to run real user questions against the model:

  • Find approved Australian lifestyle images for social.
  • Find assets for the 2026 campaign that expire within 90 days.
  • Find all English product images approved for web use.
  • Find assets that are activation-ready but not yet published.

If those searches can't be run reliably, the metadata model is incomplete — that is the signal, not a nice-to-have.

F · Permissions

The control model

Who can see, change, download, approve, or administer the asset?

Know the difference between view, edit, metadata editing, download, delete/move, folder administration, workflow participation, and collection sharing. A useful pilot exercises at least five roles: a contributor who uploads and edits metadata; a reviewer who approves but can't change the governance model; a consumer who searches and downloads approved assets; a restricted user who can't reach unreleased assets; and an administrator who manages schemas, profiles, tags, and permissions. Do not assume a Workfront user has equivalent AEM rights — validate access in both systems.

Making assets usable

Processing, renditions, and processing profiles

On upload, AEM can extract metadata, generate thumbnails and previews, create web or mobile renditions, apply configured processing, and trigger post-processing. In AEM as a Cloud Service, asset microservices perform this processing in the cloud, and processing profiles define the renditions and behavior applied to a folder. The Cloud Service model replaces much of the legacy asset-processing workflow behavior — don't carry the old default assumptions across.

Design implication

A folder is not only an organizational choice. It can determine the metadata defaults, the processing profile, the renditions generated, and the access model — so folder design has to be reviewed by both the DAM governance owner and the AEM technical administrator.

The source

Workfront — the production context that feeds the DAM

A · Projects & custom forms

Where the production context lives

Workfront holds the project or campaign, the request or brief, tasks, approvals, documents, custom fields and forms, and production status. Custom forms matter most here, because their fields become the source for AEM metadata mapping. For each field, be able to say which object owns it (project, task, or document), whether it's required, who can edit it, whether its values are controlled, and whether it has a corresponding AEM property.

B · Linked folders

Connecting the project structure to AEM

Linked folders connect a Workfront project structure to an AEM folder structure — a typical pattern nests Year → Portfolio → Program → Project under an AEM root. The configuration can define the AEM parent path, the hierarchy, the project status that triggers creation, portfolio/program and custom-form conditions, child folders, and naming rules.

Governance questions to settle

  • Who may create a linked folder, and what triggers one?
  • What prevents duplicate folders?
  • Who owns the folder after the project closes?
  • Can users create folders outside the approved structure?
  • What happens when a project is renamed or archived?

C · Metadata mapping & sync

Carrying fields from Workfront into AEM

The integration maps Workfront fields to AEM metadata properties:

Workfront fieldAEM property
Campaign namecampaignName
Brandbrand
Marketmarket
Languagelanguage
Rights expiryrightsExpiryDate
Approval stateapprovalStatus

For each mapping, pin down the source system, target field, direction, data type, allowed values, transformation rule, owner, overwrite behavior, and test status. Note that explicitly mapped values may overwrite the corresponding AEM values when an asset or a new version is sent again.

The rule to remember

If Workfront owns a mapped field, don't let users independently maintain the same field in AEM without a documented exception — otherwise no one knows which value is authoritative.

Where to draw the line

Native connector vs Fusion — and when to escalate

Use the native connector

Low-code, standard handoff

  • Standard Workfront-to-AEM asset delivery
  • Metadata mapping
  • Linked folders
  • Standard project-to-DAM structure
  • Low-code configuration

Consider Fusion or APIs

Escalation path

  • Pre-send validation & conditional rules
  • Data transformation & external lookups
  • Automated orchestration
  • Reverse sync from AEM to Workfront
  • Complex error handling & multi-system updates
Standard handoff→Native connector
Need validation or automation around the handoff→Native + Fusion
Need transformation, reverse sync, or multi-system orchestration→Fusion / APIs
Caution

Don't design bidirectional synchronization casually. Adobe's own discussion materials flag the risk of update loops and the need to define a clear source of truth for every field.

Recommended first learning activity

Take one representative asset — say a campaign image — and trace it end to end. For each step, record the product feature used, system of record, responsible owner, required configuration, expected result, and failure scenario. This teaches the product far better than studying each feature in isolation.

  1. Workfront brief
    Request or campaign brief kicks off the work
  2. Custom-form metadata
    Structured fields captured on the project / document
  3. Approval
    Asset reaches an approved, final state
  4. Final asset / document
    The file that gets handed off to AEM
  5. Linked AEM folder
    Governed destination created from project context
  6. Metadata mapping
    Workfront fields written to AEM properties
  7. Processing profile
    Asset microservices apply the folder's profile
  8. Renditions
    Thumbnails, web, and mobile outputs generated
  9. Search & reuse
    Discoverable by metadata, tags, and facets; added to collections
  10. Rights expiry or archive
    Lifecycle controls retire or flag the asset
