    How AI systems reach websites

    AI answers are assembled, not fetched. A single response may draw on a search index, a live agent fetch, a cached copy and an ingestion pipeline at once — which is why AI visibility can never be explained by one crawler or one request in your logs.

    Audience · Technical & marketing teams Scope · Acquisition → distribution → generation Companion to · Technical SEO & GEO
    01 Overview

    One statement, three layers

    The idea that "AI reads your website" is directionally right but conflates three separate things.

    What people call AI traffic is not one behaviour. It spans how a system acquires website data, where that data is stored or served from, and how it is selected and used when an answer is generated. These layers are not mutually exclusive — a single answer routinely involves several of them.

    The three layers

    Acquisition — how a system obtains website data (crawl, search, agent fetch, feed).
    Storage & distribution — where data is retained or served from (index, cache, corpus).
    Answer generation — how data is retrieved, ranked and used in the response.

    This view deliberately simplifies the picture to four acquisition paths and one generate-and-cite funnel. Here is how each part maps to the rest of this reference — and where the vocabulary differs:

    In the summary aboveIn this reference

    2 · Direct Page FetchChatbot and action-agent browsing (§6) — the live, in-session path
    3 · AI CrawlerDirect crawling (§5) — scheduled, indexes for later

    The next section unpacks this into the fuller taxonomy — eight mechanisms rather than four consolidated paths — and the same "one or several paths" logic drives the whole reference.

    A concrete example. An assistant might receive a question, query its own search index, retrieve a page last crawled hours earlier, fetch one result directly to verify it, combine that with other sources, generate an answer using retrieval-augmented generation, and cite the page — all without producing a conventional human visit.

    The critical distinction: access is not use

    These are all different events, and they do not imply one another:

    • Crawled but never cited.
    • Indexed but not fetched at answer time.
    • Fetched directly but not used in the final answer.
    • Used in an answer with no live request to the origin.
    • Cited from a cached or third-party copy.
    • Present in a training corpus but not retrieved live.
    • Visited by an agent without generating a human analytics session.
    Key distinction

    A request in your CDN log proves a client accessed a URL. It does not prove the content was indexed, retrieved for a query, included in an answer, cited, or read by a human. Equally, the absence of a live request does not prove the page had no influence — the system may have used a cache, an index, or a third-party copy.

    The full lifecycle, from access to outcome:

    Website access
    Content processing
    Indexing or storage
    Retrieval
    Selection and ranking
    LLM context
    Generated answer
    Citation, mention, referral — or no click
    02 Taxonomy

    A better taxonomy of AI website access

    Sorting the mechanisms by their layer makes the whole picture legible — and the trigger column shows the axis that matters most for reading your logs: whether a mechanism runs on the provider's schedule or fires live, in-session, only when a user asks.

    Three of these fire live, in-session — the chatbot and action-agent fetches, plus the answer-time leg of RAG; the rest run ahead of time on a schedule. That single distinction is why a page can shape an answer with no live request, and why a live request does not prove the page was used.

    The most important correction

    RAG is not a seventh crawler. It is the answer-generation architecture that can consume the output of any of the other mechanisms — a search index, a proprietary index, a live fetch, a cache, or an ingestion pipeline.

    A single answer can touch several mechanisms in sequence: a crawler or feed supplies an index, a retriever selects passages, and a live agent fetch — a chatbot reading to answer, or an action agent operating to complete a task — hits the page directly.

    04 Acquisition

    Search retrieval

    Search retrieval is when an AI system obtains candidate pages from a search index or search service. The index may be owned by the provider, licensed from a search partner, built by a third party, or a hybrid of several. The system does not download the web for every question — it submits a query and receives candidate documents, URLs, snippets, metadata or passages.

    It is usually index-first

    In an index-first model the provider has already processed the site before the user asks. The website may therefore receive no request at answer time, even though its indexed information contributed to the answer.

    # Earlier
Website → Search crawler → Search index

# At answer time
User prompt → Search index → Retrieved representation → AI answer

    The index may hold page text, titles, headings, snippets, links, structured data, language signals, the canonical URL, last-crawled information and historical versions. The system may retrieve the whole document, a passage, a snippet, or only metadata.

    Why technical SEO still matters

    Search retrieval is the mechanism most tied to traditional SEO because it depends on the health of the search index: crawlability, indexability, sitemap inclusion, canonicalisation, internal links, rendering, HTTP status, page speed, regional accessibility, structured data and index freshness. Most answer engines still retrieve candidate pages through search, so strong SEO is one of the largest inputs into AI visibility.

    Query fan-out

    Systems rarely submit only the literal prompt. They decompose it into several retrieval queries. Ask "Which PDF editor is best for a regulated enterprise?" and the system may also search for enterprise security support, compliance workflows, electronic signatures, product comparisons and vendors serving regulated industries.

    The implication is technical, not editorial: relevant URLs need to be independently discoverable, important information must not sit only behind an inaccessible client-side interface, canonical URLs should be stable, and related pages should have crawlable links.

    Retrieval does not guarantee citation

    A page can be retrieved and still not cited — used only as background, combined with others, or passed over for a different source. The stages are separate:

    Retrieved≠ Selected≠ Cited≠ Clicked≠ Converted

    Failure modes

    Search-retrieval failures usually trace back to the index representation, not the live page: the page is not indexed; it is indexed under an obsolete canonical URL; its key information is absent from the indexed copy; it is too slow or unreliable to crawl; it is blocked by robots, WAF or authentication; the index holds an older version; a duplicate or alternate-language URL wins; the relevant content exists only after JavaScript; or a third-party page is ranked above the first-party source. Begin the investigation with the index, not only the browser.

    05 Acquisition

    Direct crawling

    Direct crawling is the systematic fetching of pages by an automated client. The crawler requests a URL, reads the response, extracts links and metadata, stores or forwards the result, and repeats on its own schedule. It is generally provider-driven rather than triggered by a specific question.

    Training crawling is not live retrieval

    A training crawler may fetch a page today while a model update happens much later. The origin need not be contacted when the answer is produced.

    January:  Website → Training crawler → Training corpus
Later:    Corpus → Model training / fine-tuning
Later:    User prompt → Model response

    So a page can shape a model's learned behaviour without appearing as a current citation — and blocking a training crawler does not necessarily block search indexing, user-triggered fetches, AI search retrieval, agentic browsing, or third-party indexes. Providers use separate user agents for these functions.

    One provider, many crawlers

    A single provider typically operates several distinctly-named crawlers, and the current pattern is a consistent three-way split — training, search index and user-triggered fetch (the last of these is what the Agent Type filter labels Chatbots):

    ProviderTrainingSearch indexUser-triggered fetch
    OpenAIGPTBotOAI-SearchBotChatGPT-User
    AnthropicClaudeBotClaude-SearchBotClaude-User
    Perplexity—PerplexityBotPerplexity-User
    GoogleGoogle-Extended *Googlebot †—

    * A robots.txt control that opts content out of Gemini and Vertex AI training and grounding — not a separate crawler.   † The classic search crawler; it also feeds AI Overviews and AI Mode.

    The Google-Extended trap

    You cannot block Google's AI answers without blocking Google Search itself, because both run through Googlebot. Google-Extended only opts you out of Gemini and Vertex training and grounding; it does not change how Googlebot crawls, indexes or ranks your pages. Treat AI-search visibility and training opt-out as separate levers.

    The operational consequence:

    Allowing a search crawler        ≠  allowing the training crawler
Blocking a training crawler      ≠  blocking the user-triggered fetcher
Allowing a user-triggered fetch  ≠  placing the page in the search index
    Verify, don't trust the string

    A declared user agent can be spoofed, and compliance varies — some crawlers (for example ByteDance's Bytespider) have been documented ignoring robots.txt, and undeclared crawling has been observed in the wild. For high-confidence identification, verify the requesting IP against the vendor's published address ranges rather than relying on the user-agent header alone. Note too that user-triggered fetchers (ChatGPT-User, Claude-User, Perplexity-User) may treat an explicit human request more like a browser visit than a crawl, and so may not apply robots.txt the same way.

    Rendering capability varies

    Direct crawlers differ widely: some parse only the initial HTML, some execute limited JavaScript, some render in a browser-like environment, some stop after a short timeout. The safe assumption is neither "all AI crawlers run JavaScript" nor "none do", but:

    Safe rule

    Essential information should be available in the initial HTML or server-rendered output, even when JavaScript enhancement is used.

    06 Acquisition

    Agentic browsing

    Agentic browsing is when an AI agent visits pages dynamically while responding to a request. Unlike a scheduled crawler, the agent may start from a user-provided URL, search, follow links, read several pages, compare information, navigate pagination, inspect forms, use a browser session and perform a sequence of actions before returning a result.

    Adobe Brand Visibility treats this as agentic traffic: direct requests made by LLM bots or agents when they crawl or fetch pages to produce AI results — distinct from referral traffic, where a human clicks a link in an AI answer.

    Chatbot vs action agent — the distinction that gets conflated

    These two are the pair most often confused, because both are live and user-triggered and both can drive a real browser — at the fetch layer they look alike. The difference is purpose, not mechanism: a chatbot reads your page to answer; an action agent operates your page to complete a task.

    Chatbot

    Two traps

    Rendering is not the tell. Both categories may execute JavaScript and render the page; intent is what separates them, not whether the DOM was built. "Agent" in a name is not the tell either. Google AI Mode and GoogleAgent-URLContext are classified as chatbots — their job is to ground an answer — despite "Agent" in the string. Only the operator-class agents (browser-operating, computer-use) count as action agents.

    Usually request-specific

    Agentic browsing is typically triggered by a task, narrower than a broad crawl, more immediate than scheduled indexing, short-lived, potentially multi-page and potentially stateful.

    User: Compare the pricing of three products.

Agent: search A → fetch A → search B → fetch B → fetch C → compare → present table

    Those requests may appear in CDN or origin logs but produce no browser analytics events.

    What triggers a live chatbot fetch

    A chatbot-class fetch (ChatGPT-User, Claude-User, Perplexity-User, Google AI Mode and peers) is synchronous and in-session — it fires at answer time, only when the assistant decides it needs to read your live page to respond. It is never scheduled. The usual triggers:

    • The user supplies a URL — pastes a link to summarise, compare or extract from. The assistant fetches that exact URL. The cleanest, most deterministic trigger.
    • The query needs fresh or specific information the model won't answer confidently from memory — recency-sensitive asks ("latest", "today", pricing, current status) or long-tail specifics.
    • Post-search verification — a search step returns candidate URLs and the assistant fetches the top one or two live to confirm exact wording before composing the answer or citation.
    • Follow-up or citation drill-down — the user expands a cited source or asks a follow-up needing detail the snippet did not carry.
    • Retrieval-native product mode — browsing is enabled or the product fetches live per query by design.
    And when it does not fire

    No live chatbot fetch occurs when the answer comes from the model's parametric knowledge, from the provider's pre-built search index (that was an earlier scheduled *-SearchBot visit, not a live hit), or from a cache. A platform can therefore answer about your page — even cite it — with no chatbot request in your logs at all. This is the "access ≠ use" rule from the other direction.

    Two consequences follow from the in-session nature. Because a person is waiting, these fetchers are latency-intolerant — a slow page or a redirect chain can drop you from the answer. And because a human initiated the request, they may treat robots.txt more like a browser visit than a crawl. Platform tendency varies: Perplexity is retrieval-first and fetches near-constantly; ChatGPT and Claude fetch more selectively; Google AI Mode leans on Google's existing index, so much of its grounding never reaches your origin as a live hit.

    Direct fetch vs browser-like interaction

    An agent may use raw HTTP retrieval, full browser rendering, or a hybrid — search the index first, then directly fetch and render only the selected URL. The implementation differs by platform, product tier, request, tool mode, URL type, security policy and whether an interactive task is required. Test each important agent category separately rather than treating "AI traffic" as one client.

    The JavaScript-hidden-content risk

    A browser-based agent may be capable of executing JavaScript without choosing to wait for hydration, click every tab, expand every accordion, scroll infinite content, dismiss a cookie banner, submit a form, authenticate or retry a failed API call. A human sees the information; the agent does not.

    Human browser: Initial HTML → JS → API → click → expanded information
Agent:         Initial HTML → parse → no interaction → incomplete information

    Progressive enhancement is the fix: put essential information in the initial HTML, use JavaScript for optional behaviour, make links real anchors, keep important tables in the server-rendered page, and avoid requiring a click or an API call to expose core facts.

    Zero-click influence

    Agentic traffic (agent → website) is not referral traffic (human → website after an AI answer). A human may never visit even though an agent read the page and used it. Analytics tags generally measure the human click-through, so agentic traffic is observed through server-side, CDN or WAF logs — not browser analytics.

    07 Distribution

    Cached pages

    A cached page is a previously fetched or processed representation that can be served without contacting the origin at the time of use. Caching exists at many layers: browser, CDN/edge, reverse proxy, search-engine cache, provider page cache, search-index snapshot, vector-index document store, and retrieval-context cache. These are not identical.

    HTTP and CDN caching

    If the CDN holds a valid cached response, the origin may never see the request. A cache can therefore hand a crawler an older version, a cached redirect or error, an incomplete page, a different regional variant, or a bot-specific response. Controls include Cache-Control, ETag, Last-Modified, cache keys, TTL, purge rules, stale-while-revalidate and Vary.

    Search-index snapshots and provider caches

    A search index is effectively a structured, processed snapshot of your content — it can serve retrieval without contacting the site at answer time, which is one reason a page can be cited with no matching live request in your logs. Providers may additionally retain parsed HTML, extracted passages, metadata, snippets, embeddings, source rankings and citation mappings, usually in provider-specific ways that are not publicly visible.

    Deployment ≠ instant visibility

    A change that has reached your origin may not be visible to every AI system immediately, owing to crawl scheduling, index-refresh intervals, cache TTL, asynchronous ingestion, embedding refresh, ranking recalculation, regional replication and citation-index updates.

    Cache freshness ≠ content freshness

    A page can be editorially current but technically stale downstream:

    Origin:        current version
CDN:           old version
Search index:  older version
Vector index:  older still
AI answer:     stale fact

    Useful validators help systems decide whether to reuse or refresh — but they do not guarantee immediate recrawling:

    Last-Modified: Tue, 10 Mar 2026 14:32:00 GMT
ETag: "page-version-20260310"
Cache-Control: public, max-age=300
    Measurement nuance

    For Gemini specifically, much answer activity can be served from Google's general index or Googlebot cache rather than a live Gemini-agent fetch. In that case the site may receive no live Gemini request, activity may attribute to Googlebot, and live agentic-traffic metrics can under-represent total AI influence. Read Gemini agentic traffic as observed live-fetch activity, not as the whole picture — a measurement distinction, not a claim about every answer.

    08 Processing

    Ingestion pipelines

    An ingestion pipeline is a batch or streaming process that turns pages or other sources into a form an AI system can search or retrieve. Inputs may come from crawling, sitemaps, RSS/Atom feeds, APIs, structured data feeds, uploads, enterprise connectors, cloud storage, partner feeds, search APIs, third-party indexes, common web datasets or private documentation. It is not a download — it transforms.

    Fetch/receive → parse → remove boilerplate → extract text → detect language
→ normalise metadata → deduplicate → chunk → embed → build indexes → attach URL & citation metadata

    The stages that break things

    Boilerplate removal can misfire on ambiguous structure, stripping main content or keeping navigation. Chunking splits large documents into passages — and poor boundaries can separate a heading from its explanation, a product name from its specification, a warning from the condition it qualifies, or a table header from its values. A system may then retrieve a passage without the surrounding context it needs.

    Ingestion does not always require a public crawl

    A site can enter an AI system through a direct data connection — CMS to API or feed to an enterprise vector index — with no crawler request to the public site at all. This is common in enterprise search, internal knowledge assistants, support and documentation assistants, product catalogues and private RAG.

    The requirements then shift to feed reliability, API authentication, document IDs, source URLs, access-control metadata, versioning, deletion propagation, chunk quality, citation metadata and refresh frequency.

    No agent type of its own

    Ingestion is a processing stage, not a live agent, so nothing in the Agent Type filter (§15) maps to it — observe it through feed, API, connector and batch-job logs plus index presence, not agentic traffic. When a pipeline does pull from the open web, the request you see is an existing crawler — a training bot or a web search crawler (§3) — doing the fetch, with the ingestion work happening server-side afterwards.

    "Public" is not "usable"

    A page can be perfectly accessible and still fail ingestion — the parser extracts navigation, the main content needs JavaScript, a challenge/CAPTCHA is returned, the canonical is wrong, the source URL is not stored with the text, headings are stripped, tables become unreadable, chunk boundaries are poor, duplicates flood the index, deleted content lingers, or a feed fails silently.

    09 Distribution

    Third-party indexes

    A third-party index is a searchable store maintained by another organisation and used by an AI system as an external source — a general or specialised search engine, an industry database, a commerce index, a review platform, an open-web dataset, a documentation index or a data aggregator. The provider queries that index rather than crawling your site directly, so at answer time your site may receive no request.

    Website → Third-party crawler → Third-party index
                                     ↓
AI system → Third-party search API → Retrieved result

    Your visibility inherits their requirements

    If an AI system relies on a third-party index, your visibility depends on that index: you may need to be crawlable by the third party, present in its sitemap or feed, reachable from its regions, renderable by its crawler, free of WAF challenges, properly canonicalised and current in its data. Allowing one provider's crawler does not guarantee inclusion in a third-party index that the provider then uses.

    Version chains and attribution

    Third-party indexes refresh on their own schedule, creating a version chain where the answer context can lag several versions behind your origin:

    Origin V4 → CDN V4 → Search index A V3 → Third-party index B V2 → Answer context V2

    And if an answer cites a third-party page that describes or links to your brand — a review, comparison, marketplace listing or directory — you may see no direct request, no human click, yet still be influenced and cited via someone else's source. This is why visibility measurement must separate first-party source visibility, third-party source visibility, brand mentions, direct agentic access and human referrals.

    10 Orchestration

    Retrieval-augmented generation

    RAG is an architecture in which the model receives externally retrieved information as context before it generates. It does not specify where the information comes from — a search index, a vector database, a third-party API, a live page, a cache, a private repository, a structured catalogue, or a combination.

    Without retrieval:  User prompt → Model knowledge → Answer
With retrieval:     User prompt → Retriever → Passages → Context → LLM → Answer
    The orchestration layer

    RAG is the layer that connects retrieval to generation. It can consume the output of every mechanism in this reference — which is exactly why it is not a crawler.

    Retrieval types

    • Sparse — exact or near-exact terms; good for product names, error codes, version numbers, API methods and specific phrases.
    • Dense — embeddings for semantic similarity; good when the user's wording differs from the page or the question is conceptual.
    • Hybrid — combines keyword match with semantic similarity.
    • Live — retrieve an indexed passage, then fetch the live URL to verify current information, availability, wording, pricing or the citation destination.

    A multi-stage system may search broadly, retrieve candidates, rerank, fetch the top pages, extract passages, generate, then attach citations. Your site can be touched at one stage, several, or none at answer time.

    Reranking and source selection

    Retrieval returns more candidates than the model can use. A reranker weighs relevance, intent, freshness, source quality, authority, page type, language, geographic relevance, duplicate similarity, citation availability and confidence. A technically accessible page can still be excluded if its text is not extractable, it is dominated by boilerplate, its URL is unstable, its metadata is weak, the retrieved chunk lacks context, or a more relevant duplicate exists.

    Context packing

    The context window is finite, so the system chooses which passages to include. Clear headings and self-contained sections make it easier for a retriever to select a complete passage — if a page's essential qualification sits far from the claim it modifies, the retrieved context may arrive incomplete.

    Citation mapping

    Citations map generated claims back to source documents using source-URL metadata, passage or document IDs, search-result URLs, chunk provenance or provider-specific structures. A citation does not prove a live origin fetch — the URL may come from an index, a cache, a stored document or a third-party index.

    Citation≠ proof of a live origin request

    It proves the system associated the answer with a source representation — not that your origin was contacted at that moment.

    11 In practice

    How the mechanisms combine

    Real workflows chain these mechanisms differently, and each pattern implies a different technical priority.

    Search-backed RAG

    Prompt → generated search query → indexed pages → snippets/passages → rerank → RAG context → answer & citations. Impact: depends mostly on technical SEO; the origin may see no request at answer time; index freshness and search-crawler access matter; citations may rest on indexed data.

    Search plus live verification

    Index returns candidate URLs → the top URLs are fetched directly → index data is compared with live pages → answer. Impact: needs both index visibility and successful direct access; CDN/WAF behaviour, initial HTML and rendering all matter; the verification fetch may show in logs.

    User-provided URL fetch

    User supplies a URL → direct request → parse → summarise/answer. Impact: search ranking may be irrelevant; direct access, status code and response completeness are critical; the agent may not run all JavaScript; the request appears as a user-fetch agent; there may be no browser analytics event.

    Agentic multi-step browsing

    Agent searches, visits several sites, follows links, interacts, extracts facts, completes the task. Impact: link structure matters; pages must be independently accessible; important actions should not depend on fragile client-side behaviour; security boundaries must be explicit; logs may show several requests from one agent family.

    Third-party-index RAG

    Website → third-party crawler/feed → third-party index → provider queries it → RAG context → answer. Impact: the first-party site may see no request; third-party crawl and indexing policies matter; external freshness may lag; the answer may cite the third party instead of you.

    Enterprise RAG

    CMS/docs/APIs/files → authorised ingestion → chunking & vector indexing → query → permission-aware retrieval → answer. Impact: public crawlability may be irrelevant; feed/API availability, access-control metadata, deletion/version propagation and preserved source URLs are what count.

    12 Playbook

    Technical implications for website teams

    Make the initial response useful

    Do not assume every system executes JavaScript, waits for hydration or interacts. Put important information in the initial HTML, server-rendered output, semantic DOM, structured data and crawlable links. Avoid making essential facts depend only on client-side API calls, click-to-reveal components, tabs, accordions, infinite scroll, canvas rendering, browser storage, session state, authenticated requests or third-party JavaScript.

    Make every important URL independently retrievable

    A retrieval system may reach a URL without the normal site journey. Important pages should return a valid response directly, use stable descriptive canonicals, avoid unnecessary session parameters and redirect chains, and remain accessible without prior navigation state.

    Control access deliberately

    Review robots.txt, sitemaps, noindex, canonicals, authentication, CDN rules, WAF policies, rate limits, geo-blocking, challenge pages and user-agent policies. Because a provider may run separate agents for training, search indexing, user fetch, research, media and actions, a blanket rule can have unintended consequences.

    Maintain response parity

    Compare what a human browser, a search crawler, an AI search crawler, a user-triggered AI fetcher, a research agent, the CDN cache, the origin and different regions each receive — at minimum on status code, headers, title, main HTML, primary heading, important links, structured data, canonical, language, completeness, response time and cache status.

    Preserve source provenance

    When content is consumed through feeds, APIs or pipelines, carry the canonical URL, title, document ID, last-modified timestamp, version, language, access policy, content type, source system and heading path. Without provenance a system may answer but be unable to cite you correctly.

    Extractability wins citations

    Lead with the answer, keep passages short and self-contained, and use structured lists, tables and figures — studies of AI answers consistently find these formats are more likely to be extracted and cited. Anchor your entity with accurate structured data: an Organization schema tied to your brand, plus Article, FAQPage, Product or HowTo where relevant, is a disambiguation tool that helps a model connect content to the right entity and pull the correct attributes.

    On llms.txt — useful, not a silver bullet

    The llms.txt convention (a curated, plain-text pointer to your cleanest content) is an emerging signal with patchy adoption and no formal cross-vendor standard. As of mid-2026 it sits in the single-digit-percent range even among the largest sites, Google has stated it is not required for its own AI Search features, and support elsewhere is uneven. It is most worthwhile for developer-documentation and agent-facing properties. Treat it as an optional complement to robots.txt, sitemaps and structured data — never a replacement.

    Monitor server-side behaviour

    Browser analytics are insufficient for agent visibility. Use CDN, WAF, origin and reverse-proxy logs alongside Search Console, synthetic requests, user-agent classification, and status-code, response-time and cache dashboards. Adobe LLM Optimizer surfaces operational signals including agent interactions, success rate, average TTFB, agent type, unique agents and top agent.

    14 Adobe Brand Visibility

    Reading the mechanisms in Adobe Brand Visibility

    Within Adobe Brand Visibility, these mechanisms map onto separate but related signals. Reading them as one number is the most common analytical error.

    Agentic Traffic — "Are AI systems actually requesting our pages?"

    Measures direct requests from AI bots or agents to owned pages. Useful fields include agent name and type, URL, request volume, success rate, status code, TTFB, response size, region, cache status and time period. It is distinct from ordinary visitors and from human referral traffic.

    Read it by agent type, because the types imply opposite responses. A rise in chatbot traffic means you are being used as a source — the lever is extractability, and it should track with Source Visibility. A rise in action-agent or shopping-agent traffic means agents are trying to operate your site on a user's behalf — the lever is agent-navigable flows and a safe automation posture, not citation. One says "make me easier to quote"; the other says "make me easier to operate, safely".

    Source Visibility — "Are our pages used as sources in AI answers?"

    An outcome signal, not a request log. A page can show high agentic traffic and low citation visibility, or low direct traffic and high citation visibility, or no current agentic traffic yet citations from an index or cache, or many mentions but few owned-source citations.

    Referral Traffic — "Are humans arriving after an AI result?"

    Humans clicking through an AI-generated result or citation. Distinct from agentic traffic:

    Agentic=AI agent → website
    Referral=human → website after an AI interaction

    A site can have high agentic traffic and low referral traffic when AI answers satisfy users without requiring a click.

    Why platform comparisons need care

    Different platforms combine search indexes, live fetches, caches, third-party data and provider-specific agents differently. Gemini agentic traffic in particular should be read as observed live-fetch activity, while much of the underlying answer generation can lean on Google's broader index or cache. Compare platforms on like-for-like signals, not on a single "AI traffic" total.

    Two families, opposite responses

    Six of the eight values are read-oriented — the agent consumes your page to train, index, answer or research. Two — Action agents and Shopping agents — are act-oriented: the agent operates your page to complete a task. A rise in the first family says "make me easier to quote"; a rise in the second says "make me easier to operate, safely".

    Reading the Chatbots value

    Chatbot hits are live, in-session fetches fired at answer time — most often when a user supplies a URL or the query needs fresh detail (§6 covers the full trigger list). Two things to expect when you filter on this value. Volume is uneven by platform: Perplexity fetches near-constantly, ChatGPT and Claude more selectively, and Google AI Mode leans on Google's index so much of its grounding never appears here as a live hit. And a flat or low count does not mean you are not being used — index- or cache-served answers cite you with no chatbot request at all, so always read this value alongside Source Visibility rather than on its own.

    16 Diagnostics

    A technical diagnostic sequence

    When a page has low AI visibility, investigate in this order — from public access outward to the signals that separate the mechanisms.

    1 · Verify public access

    curl -I -L https://www.example.com/page

    Check the final status code, redirect count, Content-Type, Cache-Control, ETag, Last-Modified, response time and any authentication or challenge behaviour.

    2 · Inspect the raw HTML

    curl -L https://www.example.com/page

    Confirm the response itself contains the main heading, important text, links, tables, canonical URL, structured data and language metadata.

    3 · Compare raw HTML with the rendered DOM

    Diff the initial HTML against the post-JavaScript DOM, and identify anything that appears only after hydration, API calls, clicks, scrolling, tab expansion, a modal or a form submission.

    4 · Check search discoverability

    Validate robots.txt, the XML sitemap, canonical, noindex, internal links, status codes and search-index coverage.

    5 · Check AI-agent access

    Review CDN, WAF and origin logs for known search crawlers, training crawlers, user-fetch agents, research agents, action agents and unknown automated clients — and verify suspicious ones against published IP ranges.

    6 · Check response parity

    Compare responses across a browser, a search crawler, an AI crawler, an AI user-fetch agent, different regions, and CDN cache hit vs miss vs origin.

    7 · Check freshness

    Verify the deployment reached the origin, the CDN was invalidated, sitemap lastmod changed, Last-Modified and ETag are accurate, redirects point to current URLs, and structured data reflects the current version.

    8 · Separate the signals

    Do not merge crawl access, agentic traffic, search-index visibility, source citations, human AI referrals and conversions. Each is a different stage — and confusing them is what makes AI visibility feel unexplainable.

    In one line

    A website may influence an AI answer without receiving a live request, and a live agent request does not by itself prove the page was cited or used. Measure access and use as separate things.
