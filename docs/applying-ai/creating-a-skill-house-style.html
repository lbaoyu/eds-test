Package what you repeat as a skill.

Where skills come from

The re-explanation tax

The house-style skill didn’t start as a skill. It started as a paragraph I kept re-typing at the top of every session that produced an Adobe HTML deliverable.

Charcoal hero, Spectrum tokens, American English, embedded logo, no external dependencies — the same setup, every new chat, before any real work began. That repeated cost is the signal. A skill is worth writing the moment you notice you’re re-explaining the same context, conventions, or workflow often enough that the explanation has itself become boilerplate.

The test isn’t “is this complex?” It’s “have I said this before, and will I say it again?” Complexity is optional; repetition is the trigger.

It’s equally worth knowing what a skill is not for. A genuine one-off doesn’t earn one. Neither does something the model already does well unprompted — skills are consulted for work that can’t be handled trivially in a single step, so a skill for a task that needs no help will simply never fire.

Takeaway

If you’ve re-explained it twice, you’ll re-explain it twenty times. That’s the moment to capture it — not the twentieth.

The shape of the thing

Anatomy of a skill

A skill is a folder. At minimum it holds one file — SKILL.md — with YAML frontmatter and a Markdown body. Optionally, it carries bundled resources alongside it. The house-style skill is almost that minimal:

# the whole skill is a folder adobe-html-deliverable/ ├── SKILL.md # frontmatter (name + description) + instructions └── assets/ └── adobe-logo.png # embedded into every deliverable it produces

What makes that structure work is progressive disclosure — a three-level loading system. You design against it deliberately, because each level has a different cost:

Level 1

Metadata

Name + description. Always in context (~100 words). All the model sees until the skill triggers.

→
Level 2

SKILL.md body

The full instructions. Loaded only when the skill fires. Aim to keep it under ~500 lines.

→
Level 3

Bundled resources

Scripts, references, assets. Pulled in only as needed; scripts can even run without loading their source.

This gradient is why you don’t pour everything into the description. The description is a cheap, always-loaded index; the body is the manual you open once the index says this job is relevant; resources are the heavy items you fetch on demand. Put each thing at the level where its cost is paid only when it’s worth paying.

The one field that matters most

The description does the routing

Of everything in a skill, the description earns the most attention, because it is the triggering mechanism. The model sees every skill’s name and description and decides — from the description alone — whether to open the body. Get it wrong and the best instructions in the world never load.

There are two failure modes. Under-triggering: the skill stays asleep when it should have fired. Over-triggering: it grabs jobs it has no business owning. The house-style description fights both by being explicit in both directions:

--- name: adobe-html-deliverable description: Generate Adobe-branded, fully self-contained HTML deliverables in the established house style. Use ONLY for polished, customer- or field-facing single-file HTML in an Adobe / ABV / LLMO / GEO / AEM context — reference docs, pattern libraries, reports, prompt libraries — or when the user says "house-style HTML". Do NOT use for internal notes, quick markdown drafts, throwaway mockups, or non-Adobe pages. ---

Read what that description is actually doing:

  • States the output up front — a self-contained Adobe HTML deliverable — so the match is unambiguous.
  • Names positive contexts concretely (ABV / LLMO / GEO / AEM, the specific document genres) rather than gesturing at “HTML.”
  • Ships an explicit trigger phrase (“house-style HTML”) for the times you want to invoke it by name.
  • Draws hard exclusions so it doesn’t hijack every unrelated HTML request that wanders past.

One subtlety worth designing for: descriptions tend to under-trigger, so lean slightly assertive about when to fire. And because the model only reaches for a skill on work it can’t trivially do itself, aim your description at substantive, multi-step tasks — not one-liners it would handle anyway.

Takeaway

You can write the description last, but treat it first-class. It’s the only part of the skill guaranteed to be read.

Where the content comes from

Extract, don’t invent

The strongest thing about the house-style skill is that almost none of it was designed in the abstract. The tokens, the hero recipe, the accent policy — all of it was reverse-engineered from deliverables that had already shipped and worked. The SKILL.md says so plainly: the conventions are extracted from shipped deliverables, and the token block and hero are marked canonical.

That matters because invented conventions are guesses, while extracted ones are decisions you already validated in the field. Capturing a skill from real work isn’t authoring a style guide from first principles — it’s transcribing judgments you’ve already made and tested. Gather three or four of your best real outputs, and let them tell you what the rules are:

A

Find the constants

What’s identical across every good output becomes canon. Here: the token ramp and the hero recipe — promoted to non-negotiable.

B

Name the variables

What legitimately varies becomes an explicit choice, not an accident. The skill offers two nav patterns — left rail or sticky top bar — because both had shipped.

C

Cite the source

Anchoring rules to real, shipped work makes them defensible rather than arbitrary — and gives you something to point at when one is questioned.

Constants become the parts you forbid changing; variables become documented options. Everything in between is noise you can leave out.

Instructions that survive contact

Encode the why, not just the rules

A rule with no reason is fragile. The first time it’s inconvenient, it gets dropped or quietly misapplied. The house-style skill rarely states a rule without its rationale, and that’s deliberate — when the reasoning is on the page, whoever runs the skill next (model or colleague) can generalize correctly to cases you never anticipated, instead of pattern-matching the letter of a rule and missing its intent.

Two examples from the skill itself. “Single self-contained file” isn’t left as an edict — the skill explains that these files get emailed, dropped into SharePoint, and opened on locked-down customer laptops, so self-containment is the constraint everything else serves. “Quiet the red” is justified too: accent scarcity is what makes the accent read as premium.

Watch how much more portable the reasoned version is:

// Rule only — brittle Do not tint the corner lift. // Rule + reason — travels Keep the corner lift neutral white. Tinting it turns it into the colored glow this style explicitly rules out.

The first invites a plausible-looking violation — a “tasteful” red tint that breaks the whole look. The second carries the intent, so the boundary holds even in a case the author never wrote down. Prefer explaining why something matters over stacking heavy-handed MUST statements.

Takeaway

Rules tell the model what. Reasons let it decide correctly when your rules run out — which they always eventually do.

Ship the ingredients

Bundle what the output needs

If a skill’s output depends on a fixed ingredient, ship that ingredient inside the skill rather than describing it and hoping. The house-style skill bundles the Adobe brand mark as a PNG and instructs that it be embedded as a base64 data URI in every deliverable. The self-containment rule would be impossible to honor otherwise — you can’t hotlink a logo and still expect the file to open offline on a customer laptop.

This is the resources layer of progressive disclosure doing its job. The logo sits in assets/, costs nothing until a deliverable needs it, and guarantees every output uses the same correct mark instead of whatever a web search happens to surface.

Bundle thisBecause
Templates & assets
logos, icons, fonts		 The output must use the exact artifact, not an approximation the model reconstructs.
Reference data
schemas, taxonomies		 Too large or too precise to inline into the body — load it only when the task touches it.
Scripts
generators, validators		 Deterministic steps run more reliably as code, and can execute without loading their source into context.

Rule of thumb: anything the model would otherwise have to guess at, reconstruct, or fetch from the open web is a candidate for bundling.

Make correctness checkable

Ship a verification checklist

The house-style skill ends with a self-containment checklist. It turns a page of prose conventions into a pass/fail gate the output can be held against before it goes out the door — a partial view:

  • Opens correctly with the network disconnected
  • No resource loaded over the wire (no CDN, font, script, or image URLs)
  • Brand mark embedded as base64; any raster imagery embedded too
  • All colors reference :root tokens — nothing hard-coded inline
  • lang="en-US", ~16px base type, headings on a clamp() scale
  • American spelling clean; product names correct

A checklist does two jobs at once. It gives the model an explicit last-mile review step, and it hands you — or any colleague adopting the skill — an objective definition of done that doesn’t depend on having memorized every paragraph above it. The discipline is to keep every item binary and observable: “renders correctly offline” is checkable; “looks professional” is not.

A skill is never finished at v1

Test, then refine

The first draft of a skill is a hypothesis. You confirm it by running real tasks through it and reading the output with fresh eyes. The house-style skill has been refined repeatedly since its first version — American English enforcement, hero styling, spacing, CSS conventions — each pass prompted by something a real deliverable got slightly wrong. The loop is short and you run it forever:

Step 1

Draft

Write the skill from what you already know works.

→
Step 2

Test

Run it on realistic prompts — the kind a real user would actually type.

→
Step 3

Review

Read the output honestly. What did it get wrong, and why?

→
Step 4

Refine

Fold the fix back into SKILL.md, then run it again.

How you evaluate depends on the skill. For objective outputs — a file transform, a fixed workflow — you can formalize the loop with test prompts and pass/fail assertions. For subjective ones — visual style, writing voice — qualitative review is the honest evaluator; don’t force metrics onto taste. The house style sits firmly in the second camp, so it’s tuned by eye, not by a scorecard.

Either way, the refinements flow back into the SKILL.md, so the next session starts from the improved baseline. That’s the entire point of the exercise: the skill becomes the place your corrections accumulate instead of evaporating at the end of each chat.

The one habit

Every time you catch yourself correcting the same thing, that correction belongs in the skill — not in your head, and not in the next prompt.
