The mental model

One agent, many governance skills

The AEM Governance Agent — named the Experience Governance Agent (EGA) in internal product material — is the governance layer for Adobe Experience Manager. It combines natural-language requests, customer-defined policies, and live AEM context to keep content on-brand, rights-compliant, properly permissioned, auditable, and consistent across pages, assets, and channels.

The single most important framing: it is not one monolithic checker. It is a business agent that interprets a request and routes it to the specialized governance skill that can answer it — brand analysis, attribute-based access, ACL analysis, or asset-rights analysis.

  • On-brand — voice, claims, terminology, imagery, and typography evaluated against configured guidelines.
  • Rights-compliant — expiration and DRM awareness across AEM Assets.
  • Properly permissioned — effective ACLs in the repository and ABAC in Content Hub.
  • Auditable and consistent — the same governed rules applied conversationally or in batch.

How it fits together

Architecture in plain English

Five layers do the work:

  1. Interface or external client — AEM AI Assistant, CX Enterprise Coworker, or an MCP-compatible client such as ChatGPT or Claude.
  2. Orchestration and routing — the Governance Agent interprets the request and selects the relevant skill.
  3. Enterprise Context — the shared source of truth for brand rules and content standards.
  4. A specialized governance skill — brand analysis, ABAC, ACL analysis, or asset-rights analysis.
  5. AEM or Assets data — the actual pages, assets, ACLs, metadata, domains, and environments being evaluated.

The agent is exposed through standard agent protocols, including MCP and A2A. The documented AEM MCP endpoint for compatible AI clients is:

https://mcp.adobeaemcloud.com/adobe/mcp/aem

The pivotal concept

Enterprise Context: the policy source of truth

Enterprise Context is where the organization records the rules that AI should use when creating or evaluating content, so brand knowledge stops living scattered across PDFs, wikis, emails, and individual experts.

The Governance Agent uses it for two jobs: generation guidance (helping downstream agents create content correctly from the start) and validation (evaluating existing content against current rules). It can be reused by other Adobe or customer-built agents through standard interfaces such as MCP.

Context categories

CategoryAnswers
Brand VoiceHow should the organization sound?
Claim GuardrailsWhat can the organization safely or officially claim?
Market PositioningHow should the organization describe alternatives and competitors?
Design SystemHow should content look — colors, typography, components, layouts, imagery?

Rules can be scoped by segments — country or market, audience, sub-brand, experience type, and language. A global rule acts as a baseline; more-specific segment rules override it where appropriate. A German consumer landing page for a given sub-brand can inherit global rules and then apply German-language, market, audience, and sub-brand overrides.

Active versus draft configuration

Frequent source of false results

New brands, domains, rules, and checks are created as Draft. The Governance Agent uses only entities whose status is Active. Before testing a policy, confirm the brand, the domain, the relevant context rules, and the relevant checks are all Active.

The main content-policy workflow

Brand Governance

Brand Governance validates content against configured brand rules. Documented example checks cover tone of voice, messaging, terminology, claims, logo usage, typography, imagery, and text/image content. It runs both conversationally and in batch. Typical requests:

Is this page aligned with my brand?
https://www.example.com/en.html

Does https://www.example.com/product follow our brand messaging guidelines?

Show me my active brand guidelines.

Aim for findings and explanations, not a bare binary score. A useful review asks the agent to return the failed check, the evidence, the affected page element, the applicable rule, a recommended correction, and whether the finding is definite, probable, or ambiguous.

Importing a brand policy

The intended workflow:

  1. Open Governance Context in AEM.
  2. Create a brand with a name, description, and main domain.
  3. Change the brand from Draft to Active.
  4. Add the domain and set it to Active.
  5. Upload the brand policy document.
  6. Review the extracted policy summary and checks.
  7. Organize checks into categories.
  8. Edit, delete, or manually add checks.
  9. Activate the checks you want enforced.
  10. Run a test against representative pages.

A check carries a name, a natural-language rule, a brand, a category, a scope (Images, Text, or both), and a status. Do not treat extraction as perfect policy codification — review generated checks before activating, especially for legal claims, regulated language, or nuanced regional exceptions.

Batch analysis

Batch analysis covers an existing site rather than a single page. It supports a manual URL list or sitemap discovery, maximum page limits, include and exclude patterns, and page/image result views. A completed job reports total pages evaluated, aligned and non-aligned pages, overall pass rate, passed/failed/N-A/errored checks, and per-page detail.

Run a batch brand analysis for these URLs:

https://www.example.com/en/
https://www.example.com/en/products/
https://www.example.com/en/about/

Use the active Global Brand checks. Return:
1. Pass rate
2. Failed checks by page
3. Evidence for each failure
4. N/A and errored checks separately
5. A prioritized remediation list
Do not modify content.

For large sites, start with a small representative sample: a known-good page, a known-bad page, a page with images, a localized page, and a page with claims or regulated language.

Rights awareness for DAM teams

Asset DRM and expiration governance

The asset-rights skill answers expiration and DRM questions over AEM Assets metadata — a conversational replacement for spreadsheet-based audits:

Are any of my assets expiring in the next 30 days?

Which assets in /content/dam/products expired last month?

Find assets in the campaign folder that are missing expiration metadata.

Show me the assets in /content/dam/products that will expire within 14 days.

Rights awareness, not rights administration

An asset that has not expired does not prove the organization owns every regional, channel, model, or campaign right required for reuse. Generic asset-rights answers may need validation beyond expiration metadata.

Two distinct permission models

Permissions: Content Hub ABAC and AEM ACLs

These are different models and should never be conflated. Content Hub ABAC includes documented rule-management actions; the AEM repository-permission skill is documented as read-only.

Content Hub ABAC

Attribute-based access control expresses access by user or group, asset metadata, attribute values, and organizational conditions. Documented examples:

Show all existing Content Hub ABAC rules.

Create a rule that gives the Marketing group access to all assets.

Give the Sales group access to assets where marketing:segment equals EMEA.

Delete all rules that give access to external-agency.

AEM repository permission management

The AEM permission skill answers questions about effective permissions in the repository. It can explain why a principal is allowed or denied an action, resolve inherited permissions from parent paths, identify restrictions, list principals holding privileges such as jcr:write or jcr:removeNode, identify the ACL entries causing a denial, and recommend existing groups for a grant. Good prompts:

Why can sample-author not write to
https://author-p12345-e67890.adobeaemcloud.com/content/dam?

Which groups have jcr:removeNode on /content/projects/masters?

Who is denied jcr:write on /content/secure, and which ACL entries cause the denial?

Show all effective ACL entries on /content/wknd, including inherited policies.

Recommend existing groups suitable for granting jcr:removeNode and
jcr:removeChildNodes on /content/projects/masters, following least privilege.

Critical boundary — read-only

It diagnoses permissions and recommends changes, but does not modify ACLs, groups, or content on the user’s behalf.

That makes it right for support triage, access debugging, least-privilege analysis, ACL review, and explaining inherited behavior — and wrong to treat as an autonomous ACL deployment mechanism.

Identity and entitlement

Whose access the agent uses

The agent acts through the IMS identity of the signed-in user. It does not gain more access than that user has.

Practical implication

Don’t build a separate “agent ACL matrix.” If the user cannot perform an operation directly in AEM, the agent should not be expected to either — so start permission debugging with the user’s own AEM, Assets, Content Hub, or Cloud Manager permissions.

Access model layers

  1. Platform eligibility — AEM agents are available for AEM as a Cloud Service and Edge Delivery Services; AEM 6.5 LTS Managed Services is being introduced progressively; agents are not available for AEM 6.5 / 6.5 LTS on-premises.
  2. Program or commercial access — via Try Before You Buy, a trial, or an Agentic SKU, subject to rollout and organization eligibility.
  3. AI Assistant or Coworker access — the applicable AI assistant capability must be enabled.
  4. Underlying AEM solution — typically AEM Sites and/or Assets, depending on the skill.
  5. User authorization — the signed-in user needs access to the relevant content, repository, Content Hub, or environment.
  6. Page-analysis prerequisites — configure a supported domain and ensure the target URL is reachable.

The internal feature matrix marks brand governance, Content Hub permissions, and asset-expiration audits separately, with different availability across AEM CS, Managed Services, and Edge Delivery Services. Do not answer availability at the umbrella-agent level — verify the specific skill, product surface, and customer entitlement.

The same governance capability can be exposed through different surfaces:

Rollout distinction

The initial CX Coworker agentic release does not include every use case available in the AEM in-product experience. The in-app side panel is not part of that release, so conversational ABAC-policy authoring and some assets-review workflows may not yet be available there.

Current behavior vs. direction

Roadmap is not the contract

Internal material describes a broader future governance layer: Data Leak Prevention, PHI/PII detection, customer-authored data policies, regulatory and legal assessment, C2PA provenance, automated remediation, deeper Universal Editor integration, and broader permission write operations. These are valid directions — not current documented behavior.

The strongest current customer-facing contract is narrower:

  • Brand checking
  • Brand policy import
  • Content Hub permissions
  • Asset expiration and DRM-oriented queries
  • Read-only AEM permission explanation

Do not sell roadmap capabilities such as DLP or autonomous remediation as universally available.

Getting reliable answers

A prompting pattern that works

A reliable Governance Agent prompt names the intent, the target object, the scope, the applicable brand or policy, the desired evidence, the output format, and the safety boundary.

Strong prompt

Evaluate https://www.example.com/de/product against the active
Automotive Global brand.

Return:
- Passed, failed, and N/A checks
- Evidence for every failed check
- The applicable rule
- Severity
- Recommended correction
- Any uncertainty

Do not modify or publish content.

Weak prompt

Is this okay?

The weak prompt omits the target, the applicable policy, the meaning of “okay,” the required evidence, and whether changes are allowed.

Permission prompt

Explain whether user alice can edit
/content/wknd/us/en/products.

Show:
1. Effective allow entries
2. Effective deny entries
3. Inherited policies
4. Restrictions
5. The exact missing privilege, if any

Read-only analysis only.

Asset-rights prompt

Find all assets under /content/dam/campaign-2026 that:
- expire within 30 days,
- have already expired, or
- have no expiration metadata.

Return path, title, expiration date, status, and recommended follow-up.

ABAC prompt

List current Content Hub ABAC rules affecting the Marketing group
and summarize which asset metadata conditions each rule uses.
Do not change any rules.

Putting it into practice

An adoption workflow

Phase 1

Establish the source of truth

  • Gather the current brand guide
  • Identify conflicting regional / sub-brand rules
  • Create the brand and domains
  • Import the policy
  • Review extracted rules
  • Activate only approved rules

Phase 2

Calibrate with known examples

  • A page that should pass
  • A page that should fail
  • An image violation
  • A claim / terminology violation
  • A localized page
  • Record false positives and negatives

Phase 3

Operationalize

  • Run periodic batch analysis
  • Monitor new or changed pages
  • Audit assets approaching expiration
  • Review missing rights metadata
  • Use permission analysis in support cases
  • Require human approval before publishing

Phase 4

Measure value

  • Time to complete a brand review
  • % of pages passing active checks
  • Expired assets caught before reuse
  • Assets missing rights metadata
  • Time to diagnose permission incidents
  • False-positive / false-negative rates

For a security review

Questions to ask explicitly

  1. Which exact skills are enabled?
  2. Which surfaces are enabled — AEM Assistant, Coworker, or MCP?
  3. Which IMS organizations and users are entitled?
  4. Does the user identity constrain the data returned?
  5. Is the action read-only or write-capable?
  6. Which AEM environment is being queried?
  7. Are brand rules segmented by market, audience, language, and sub-brand?
  8. Which configuration objects are Active?
  9. Are policy imports reviewed before activation?
  10. Are agent interactions and governance findings auditable?
  11. Can the customer enable only selected agents or skills?
  12. Can unrelated brands or tenants share Enterprise Context?

Two open concerns to confirm, not assure

Agent enablement may not yet support sufficiently granular per-organization or per-agent selection, and Enterprise Context is oriented toward one company with related brands rather than unrelated tenants requiring hard context isolation. Treat both as questions requiring confirmation before making strong assurances.

Know the edges

The limitations that matter

  • AI responses can be inaccurate or misleading. Verify findings and proposed fixes.
  • Draft configuration is inactive. A rule that has not been activated does not govern content.
  • Policy extraction requires review. Imported documents can be interpreted imperfectly.
  • AEM permission analysis is read-only. It does not modify ACLs, groups, or content.
  • Content Hub ABAC is a different permission model from AEM repository ACLs.
  • An asset not being expired does not prove all usage rights exist.
  • Batch results can include N/A and errors, not just pass/fail.
  • Coworker and AEM Assistant may expose different subsets of skills.
  • Availability is skill-, product-, entitlement-, and rollout-dependent.

If you remember five things

The five that anchor everything

  1. Governance Agent is an umbrella business agent, not one checker.
  2. Enterprise Context is the policy source of truth.
  3. Only Active brands, domains, rules, and checks are enforced.
  4. AEM ACL analysis is diagnostic and read-only; Content Hub ABAC can have rule-management actions.
  5. Always distinguish current documented skills from internal roadmap capabilities.
