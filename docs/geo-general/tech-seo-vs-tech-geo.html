01 · Overview

Two systems, one web platform

This guide focuses exclusively on the technical disciplines behind search-engine and generative-engine visibility. It deliberately sets aside content strategy, keyword and prompt planning, brand messaging, entity management, and off-site or reputation work, and concentrates on the web platform itself.

What technical SEO does

Technical SEO makes a website accessible to traditional search engines so they can discover URLs, crawl pages, render resources, interpret page structure, index eligible pages, and rank them for relevant searches.

What technical GEO does

Technical GEO — the technical side of Generative Engine Optimisation — makes a website accessible and interpretable to AI retrieval and answer systems so they can discover relevant pages, retrieve the correct page or section, process it reliably, interpret its structure, use machine-readable signals, and represent the page accurately in an AI-generated answer.

The relationship in one line. Technical SEO is the search-discovery foundation. Technical GEO extends that foundation for AI retrieval, extraction, and answer-generation systems.

The two are not alternatives. A page that is blocked, unavailable, unrenderable, or excluded from indexing is also less likely to be reliably retrieved by an AI system. The discipline is to keep indexable surfaces efficiently crawled, rendered, indexed and ranked — while increasingly ensuring they can also be understood, retrieved and cited by AI-driven systems.

The initial-HTML consideration

One consideration runs through both disciplines and is worth stating up front: a page can look complete in a browser while exposing very little in its initial HTML. If essential information is available only after JavaScript executes — or after a user clicks, scrolls or interacts — some crawlers and AI agents may not process it reliably.

JavaScript is not the problem. The technical risk is making essential information depend exclusively on JavaScript execution or user interaction. This theme recurs in the rendering, GEO and troubleshooting sections below.

04 · Technical SEO in depth

Technical SEO in depth

4.1 Crawlability

Crawlability is the ability of a search engine to discover and request a page. A page can be valid in a browser yet still be poorly crawlable if it is blocked in robots.txt, unlinked from any crawlable page, omitted from the sitemap, hidden behind a form or session, reachable only through JavaScript events, trapped behind excessive URL parameters, caught in redirect loops, or blocked by a CDN or bot-management rule.

robots.txt

Use robots.txt to control which paths crawlers may request.

robots.txt
User-agent: *
Disallow: /account/
Disallow: /checkout/
Disallow: /internal-search/
Allow: /

Sitemap: https://www.example.com/sitemap.xml
Important distinction. robots.txt controls crawling; it is not a security mechanism. Protect sensitive pages with authentication and authorisation, not only with a disallow rule.

XML sitemaps

A sitemap should expose the canonical, publicly discoverable pages a search engine is expected to crawl.

sitemap.xml
<?xml version="1.0" encoding="UTF-8"?>
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <url>
    <loc>https://www.example.com/products/example</loc>
    <lastmod>2026-03-10</lastmod>
  </url>
</urlset>

A production sitemap should be available at a predictable URL, declared in robots.txt, generated automatically, updated when pages change, limited to canonical URLs, and free of redirects, errors and blocked URLs.

Internal links & server logs

Internal links help crawlers discover pages and understand the relationships between URLs. Use standard HTML anchors, keep important pages off click-only handlers, avoid crawl traps and orphan pages, and redirect or remove retired pages from navigation.

Server logs reveal what crawlers actually request rather than what you expect. Log analysis surfaces repeated crawling of obsolete URLs, high volumes of parameter URLs, crawling of blocked areas, rendering-related requests, bot access failures, crawl spikes, and — increasingly — differences between search-engine and AI-agent behaviour. Server-log analysis, crawl-efficiency analysis, and rendering-failure diagnosis are core technical responsibilities.

4.2 Indexability

Indexability determines whether a search engine is allowed and able to include a page in its index. A URL can be crawlable but not indexable because of noindex, an incorrect canonical, duplicate content, soft-404 behaviour, thin responses, authentication requirements, wrong status codes, conflicting robots directives, or low-quality rendering.

noindex

Use noindex when a page should be crawlable but excluded from the index. Do not use robots.txt as a substitute — if a crawler cannot access the page, it may never see the directive.

HTML head
<meta name="robots" content="noindex,follow">

Canonical URLs

Canonicalisation tells search engines which URL represents the preferred version of substantially similar pages.

HTML head
<link rel="canonical"
      href="https://www.example.com/products/example">

Canonical problems commonly arise when HTTP and HTTPS coexist, trailing-slash variants are inconsistent, query parameters produce duplicates, regional URLs are wrongly consolidated, or redirect targets do not match canonical declarations. A canonical is a signal, not a command, and should be supported by internal links, sitemaps, redirects and consistent metadata.

Common failures include returning 200 for nonexistent pages, redirect chains, redirecting all deleted pages to the homepage, intermittent 5xx responses, serving different codes to different crawlers, and returning a login page with a 200 status.

4.3 Rendering & JavaScript execution

Rendering is one of the most consequential areas shared by technical SEO and technical GEO. Search engines do not always process a page exactly as a browser does — they may receive HTML first, then process CSS, JavaScript and other resources. A page can look complete in a browser yet expose little in its initial HTTP response. The typical failure flow:

Crawler or AI agent requests the URL
Server returns a minimal HTML shell
JavaScript executes in a browser
API requests retrieve page information
Page becomes complete for a human user

This becomes a problem for automated systems that do not execute JavaScript, execute only some of it, time out before it completes, cannot complete interactions, cannot reach the APIs the page depends on, or process the initial HTML before the page is complete.

What belongs in the initial HTML

For important pages, the initial response should ideally already contain the primary heading, the principal page information, important links and navigation paths, the canonical URL, language metadata, structured data, and any key tables or specifications.

JavaScript is not inherently bad

JavaScript is entirely appropriate for progressive enhancement, UI interactions, personalisation, analytics, dynamic filtering and non-essential visual effects. The issue is not the technology.

The principle. Making essential information depend exclusively on JavaScript execution or user interaction is the technical risk. Critical information should be server-rendered, statically generated, or otherwise present in the initial HTML.
ModelTechnical descriptionMain consideration
SSRHTML generated on the server per requestStrong initial accessibility; higher server complexity
SSGHTML generated ahead of timeFast and stable for largely static pages
CSRHTML assembled mainly in the browserGreater crawler and rendering dependency
HybridServer-rendered shell with client enhancementOften a useful balance

For SEO-critical pages, important information should exist in the initial HTML or a reliably rendered document. Compare title, headings, body, links, structured data, canonical, navigation and language signals between the browser and the crawler response — a crawler should not receive a materially incomplete or contradictory version of the page.

4.4 URL architecture

Sound URL architecture is stable, predictable, descriptive, consistent, and free of unnecessary parameters.

# Preferred
https://www.example.com/products/pdf-editor

# Less desirable
https://www.example.com/page?id=8427&src=nav&session=abc123

Avoid changing URL structures without a migration plan: URL inventory, one-to-one redirect mapping, canonical updates, sitemap updates, internal-link updates, status-code monitoring, and validation of traffic and crawl behaviour.

4.5 Site architecture & internal linking

This concerns the technical relationship between pages, not content planning. A crawlable architecture provides a clear hierarchy, accessible navigation, breadcrumb markup where appropriate, direct paths to important pages, and no orphan pages or infinite faceted-navigation combinations.

/
├── products/
│   ├── product-a/
│   └── product-b/
├── documentation/
│   ├── getting-started/
│   └── reference/
└── support/
    ├── troubleshooting/
    └── contact/

Technical controls should prevent duplicate paths, navigation-generated URL explosions, links to non-canonical or blocked pages, JavaScript-only link handling, and deeply buried pages with no crawlable path.

4.6 Structured data & semantic markup

Structured data provides machine-readable signals about the page and its objects. Common Schema.org types include Organization, Product, Article, FAQPage, HowTo, BreadcrumbList, SoftwareApplication and WebPage.

JSON-LD
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "WebPage",
  "url": "https://www.example.com/products/example",
  "name": "Example product",
  "isPartOf": {
    "@type": "WebSite",
    "url": "https://www.example.com/"
  }
}
</script>

Use valid JSON-LD, ensure the markup matches the page, avoid contradictory values, associate it with one canonical URL, validate automatically, and remove schema from retired pages. Structured data does not guarantee rankings or AI inclusion; its purpose is to reduce ambiguity for automated systems.

Semantic HTML

Use HTML elements according to their structural meaning so automated systems can distinguish main content, navigation, headings, sections, lists, tables, articles and complementary information.

HTML
<main>
  <article>
    <h1>Example product</h1>
    <section aria-labelledby="overview-heading">
      <h2 id="overview-heading">Overview</h2>
      <p>...</p>
    </section>
  </article>
</main>

4.7 Performance & availability

Performance is a visibility requirement because crawlers and users need reliable access. Monitor server response time, time to first byte, Core Web Vitals, JavaScript execution cost, asset failures, cache-hit behaviour, CDN availability, error rates, and regional availability — for both human browser sessions and automated crawler and agent requests.

Enhanced · Aug 2026 The current Core Web Vitals triad is Largest Contentful Paint (LCP) for loading, Interaction to Next Paint (INP) for responsiveness — which replaced First Input Delay in 2024 — and Cumulative Layout Shift (CLS) for visual stability. Measure INP rather than FID in any current page-experience audit.

4.8 International & regional technical SEO

For multi-language or multi-region sites, technical controls include language-specific URLs, hreflang, correct language declarations, regional canonicalisation, sitemap segmentation, and consistent availability by location.

HTML head
<link rel="alternate" hreflang="en-us"
      href="https://www.example.com/us/product">
<link rel="alternate" hreflang="en-gb"
      href="https://www.example.com/uk/product">
<link rel="alternate" hreflang="x-default"
      href="https://www.example.com/product">

Incorrect implementation can cause one market to replace another in search, wrong-language results, duplicate regional pages, redirect loops, and inconsistent AI retrieval by market.

05 · Technical GEO in depth

Technical GEO in depth

5.1 What technical GEO means

Technical GEO is the practice of making web resources usable by AI-driven retrieval and answer systems. It covers AI-agent access, server-rendered visibility, semantic document structure, machine-readable markup, crawl and retrieval controls, URL stability, retrieval freshness, AI-agent observability, and CDN and edge behaviour.

What it is not. Technical GEO does not mean inserting prompts into a page or repeating AI-related phrases. It concerns whether AI systems can technically reach, parse, understand and retrieve the page.

5.2 AI-agent accessibility

AI systems reach websites through several mechanisms — search retrieval, direct crawling, agentic browsing, cached pages, ingestion pipelines, third-party indexes, and retrieval-augmented generation. Because implementations differ by platform, the technical requirements are defensive and general: keep intended public pages accessible, avoid accidental bot blocks, ensure complete responses, expose stable canonical URLs, maintain working links, monitor access logs, and avoid relying entirely on browser interaction.

The AI-crawler landscape

Enhanced · Aug 2026 The base material treats AI-crawler behaviour as undifferentiated. In practice, the major providers now run separate bots for separate jobs, and the single most consequential technical decision is not blocking the retrieval layer by accident. The distinction below did not exist two years ago and is now the foundation of every robots and bot-management decision.

Two operational traps are worth internalising. First, a broad User-agent: * disallow can silently take out the retrieval layer along with everything else — the most common way a brand quietly disappears from AI answers. Second, Google's AI Overviews run through Googlebot; you cannot opt out of them without also leaving classic Search.

A common posture — stay citable while declining to donate training data — looks like this:

Disallow: /

Verify User-agent compliance is opt-in and strings can be spoofed, so treat robots.txt as a norm rather than a guarantee. Confirm actual behaviour in server and CDN logs, and grep for the declared substrings (GPTBot, OAI-SearchBot, ClaudeBot, PerplexityBot, and their user-fetch variants).

5.3 JavaScript-hidden information & AI bots

This issue deserves special emphasis: a page can pass a basic browser test while failing an AI retrieval test. The two clients often see very different documents.

Browser view
Requests the URL
Receives the application shell
JavaScript executes; API calls complete
Displays full information
Automated-client view
Requests the URL
Receives the initial HTML
JavaScript is not run or does not complete
Sees an incomplete document

The AI system may therefore miss the main page information, important links, product specifications, tables, navigation paths, structured data, frequently requested details, sections hidden behind tabs, and anything loaded after user interaction.

Recommended pattern

Split the page so that meaning lives in the initial HTML and convenience lives in JavaScript:

layering
# Initial HTML — meaning
- Primary heading
- Main page information
- Important links
- Key specifications
- Canonical URL
- Structured data

# JavaScript layer — convenience
- Interactive filters
- Visual enhancements
- Optional personalisation
- Non-essential interface behaviour
Progressive enhancement is safer than progressive disclosure of essential information. Critical information should be available in the initial HTML, the server-rendered output, or a statically generated page.

A quick validation is to fetch the raw response and compare it with the fully rendered browser DOM:

shell
curl -L https://www.example.com/example-page

Verify the initial response contains the primary heading, main text, important links, canonical URL, structured data, language metadata and required product attributes — without JavaScript enabled.

5.4 Semantic document structure

Retrieval systems need to identify the structure of a document: one primary h1, a logical h2/h3 hierarchy, semantic sections, proper lists and tables, descriptive links, explicit boundaries, and correct use of article, main, nav, section and aside.

HTML
<main>
  <article>
    <header><h1>Example product</h1></header>
    <section aria-labelledby="specifications">
      <h2 id="specifications">Specifications</h2>
      <table>
        <thead>
          <tr><th scope="col">Attribute</th><th scope="col">Value</th></tr>
        </thead>
        <tbody>
          <tr><th scope="row">Platform</th><td>Web</td></tr>
        </tbody>
      </table>
    </section>
  </article>
</main>

This is a parsing concern, not a content-strategy recommendation. The objective is to make document boundaries and relationships unambiguous.

5.5 Structured data for AI retrieval

Schema.org markup supports AI retrieval by exposing machine-readable information. Useful types include WebPage, Organization, Product, SoftwareApplication, BreadcrumbList, FAQPage, HowTo and Article. Keep the markup present in the server response, valid, consistent with visible page information, associated with the canonical URL, and updated during deployments.

JSON-LD
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "SoftwareApplication",
  "name": "Example application",
  "url": "https://www.example.com/application",
  "applicationCategory": "BusinessApplication",
  "operatingSystem": "Web"
}
</script>

5.6 llms.txt & AI discovery files

Some implementations expose an llms.txt (and llms-full.txt) file to publish LLM-relevant URLs and site structure.

llms.txt · conceptual
# Example site

## Documentation
- https://www.example.com/docs/
- https://www.example.com/docs/getting-started

## Product reference
- https://www.example.com/products/example
- https://www.example.com/products/example/specifications
Enhanced · Aug 2026 The base material calls llms.txt an emerging convention. Here is the 2026 reality, sharpened. Site-side adoption sits around one in ten domains, but engine-side pickup for answer surfaces is negligible — server-log studies across hundreds of millions of AI-bot visits find the file is almost never fetched, and no major provider has committed to consuming it in production search or answer systems. Google has said, on the record, that it does not support it. So do not expect llms.txt to lift citations, and never treat it as an access-control mechanism — that job stays with robots.txt and authentication.

Where it does earn its place: as a low-cost, machine-readable routing surface for agentic and coding assistants that consume a curated map rather than crawling an entire site, and — as metered-crawl models emerge — as a cost-governance lever, since an agent fetching a curated map plus a few targeted pages is far cheaper than scraping fifty. Treat it as a business-to-agent convenience, keep it synchronised with the site, and keep expectations grounded. The strongest technical implementation remains public access to intended URLs, accurate HTML, stable canonicals, valid sitemaps, correct robots behaviour, server-rendered critical information, and observability through logs and testing.

5.7 CDN, firewall & bot-management behaviour

A page can be technically public yet inaccessible to AI systems because of infrastructure controls — CDN bot rules, WAF policies, rate limits, geo-blocking, IP allowlists, user-agent filtering, challenge pages, CAPTCHA responses, or edge-rendered variants. A common failure pattern:

observed behaviour
Human browser  → complete page
Search crawler → partial page
AI agent       → 403, challenge page, or empty shell

Verify what each client receives: request the page with different user-agents, compare status codes and response bodies, review CDN and WAF logs, test from multiple regions, and check whether bot traffic is routed to a different origin. The intended public representation must be available to legitimate automated clients without weakening security for private resources.

Enhanced · Aug 2026 A newer infrastructure dimension: metered crawling. Edge platforms have begun offering pay-per-crawl controls (using the HTTP 402 Payment Required response) that let operators charge or gate AI-crawler access per request. This turns curation and retrieval efficiency from a nice-to-have into a cost-governance control, and adds a new class of access failure to watch for in logs.

5.8 Retrieval freshness & deployment invalidation

AI answers can depend on retrieved pages, cached content, or previously observed versions of a URL. Freshness controls include accurate Last-Modified headers, correct ETag behaviour, updated sitemap lastmod, cache invalidation after deployment, stable redirect targets, and consistent origin and CDN content.

HTTP response headers
HTTP/2 200
content-type: text/html; charset=UTF-8
last-modified: Tue, 10 Mar 2026 14:32:00 GMT
etag: "page-version-20260310"
cache-control: public, max-age=300

A freshness problem occurs when the origin has the new page but the CDN still serves the old one, the sitemap shows a stale date, the canonical points to an old URL, the AI agent receives a cached error, or a retired page remains discoverable. This is infrastructural, not editorial: the concern is whether discovery signals accurately reflect the deployed version.

5.9 AI-agent observability

Traditional analytics may not show all automated AI access, so technical GEO requires multiple data sources — CDN, WAF and origin logs, search-console data, synthetic tests, AI-agent user-agent data, referral analytics, application monitoring and deployment records. Useful fields include timestamp, user-agent, requested URL, status code, response size and time, cache status, referrer, region, origin, WAF action and bot classification.

Because agentic access and referral traffic differ, an AI agent may access a site without generating a conventional human referral session — which is precisely why log-level observability matters more here than page-tag analytics alone.

07 · Standards

Technical implementation standards

7.1 Minimum page-level standard

Every important public page should have a 200 response when active, a stable canonical, a crawlable path, sitemap inclusion, a server-rendered primary heading and critical information, a logical heading hierarchy, valid HTML and structured data, no accidental noindex or contradictory canonical, no unnecessary redirect chain, no essential information hidden exclusively behind JavaScript or interaction, acceptable performance, and correct language and regional signals.

7.2 Minimum site-level standard

Every site should have a working robots.txt and XML sitemap, automated sitemap generation, centralised redirect management, canonical governance, rendering tests, structured-data validation, crawl monitoring, server-log access, CDN and WAF monitoring, deployment invalidation, error-rate monitoring, AI-agent access monitoring, and a process for discoverability incidents.

7.3 Deployment pipeline checks

Technical SEO and GEO checks should run as part of deployment.

Automated checks should fail or warn when the canonical is missing, a page unexpectedly returns noindex, the sitemap contains a redirect or 4xx, the primary heading disappears, server-rendered HTML is empty, structured data becomes invalid, a page returns a challenge, a deployment creates a redirect loop, a new URL is missing from the sitemap, a retired URL returns a soft 200, or essential information disappears from the initial HTML.

08 · Playbooks

Technical troubleshooting playbooks

8.1 A page is not appearing in traditional search

  1. Does the URL return 200?
  2. Is it blocked by robots.txt?
  3. Does it contain noindex?
  4. Is the canonical pointing elsewhere?
  5. Is it in the sitemap and linked internally?
  6. Does the server-rendered HTML contain the page?
  7. Does it return a soft 404, or sit behind redirects?
  8. Are there repeated server or CDN errors?
  9. Is the page accessible from the target market?
  10. Is it being crawled but not indexed?

8.2 A page is visible to users but not to AI systems

  1. What does the initial HTML response contain?
  2. Does the AI agent receive a 403, 429 or challenge?
  3. Is it blocked by CDN or WAF rules, or behind authentication?
  4. Are critical sections loaded only through JavaScript?
  5. Are links standard anchors, and is the URL in the sitemap?
  6. Is the page canonicalised to an obsolete variant?
  7. Does it have valid semantic structure?
  8. Does the response differ by user-agent or region?
  9. Is the page requested by AI agents in the CDN logs?
  10. Has it changed without cache invalidation?

8.3 AI systems retrieve an incomplete page

Compare the raw HTTP response, server-rendered HTML, browser DOM, CDN response, AI-agent response, cached version and origin version. Typical causes: client-side rendering, API failure, lazy loading, an incorrect cache key, a bot-specific response, a WAF challenge, a timeout, mis-encoded compression, HTML truncated by an edge function, or content hidden behind interaction.

8.4 AI systems retrieve the wrong URL

Check the canonical URL, redirect chain, sitemap URL, internal links, hreflang, duplicate variants, HTTP/HTTPS consistency, trailing-slash behaviour, query parameters, retired URLs, CDN cache and structured-data URL fields. Apply the fix consistently across all technical signals rather than changing one tag.

8.5 AI-agent traffic is not visible in analytics

Check CDN, origin and WAF logs, user-agent classification, bot filtering, referrer preservation, consent behaviour and server-side analytics. Remember that an AI agent may access a site without generating a conventional human referral session, so page-tag analytics alone will under-count it.

09 · Measurement

Measurement framework

9.1 Technical SEO metrics

Track crawl requests, crawl errors and response time, indexed and excluded URLs, sitemap coverage, canonical consistency, redirect counts, 4xx and 5xx rates, rendering failures, Core Web Vitals, JavaScript errors, and organic impressions, clicks, rankings and traffic.

9.2 Technical GEO metrics

Track AI-agent request volume, success rate, 4xx/5xx rate, response time and cache-hit rate; pages accessed by AI agents; pages with incomplete server-rendered HTML; AI-readable page coverage; source visibility; citations to owned URLs; AI referral traffic; agentic traffic; and AI visibility over time. Source visibility — how often an organisation's own site is used as a source in AI answers — is distinct from a brand mention and is the signal most directly tied to technical retrieval.

11 · Roadmap

Technical implementation roadmap

Phase 1 — Technical inventory

Document domains and subdomains, URL patterns, rendering model, CMS and delivery architecture, CDN and WAF layers, sitemaps, robots and canonical rules, structured-data implementations, regional variants, authentication boundaries, log sources and AI-agent observability.

Phase 2 — Search-engine foundation

Fix crawl blocks, broken sitemaps, duplicate URLs, incorrect canonicals, redirect chains, soft 404s, noindex errors, orphan pages, rendering failures, and server and CDN errors.

Phase 3 — AI retrieval readiness

Validate initial-HTML completeness, semantic HTML and heading hierarchy, accessible structure, structured data, AI-agent access, WAF and CDN behaviour, cache invalidation, response consistency, optional llms.txt, and page-level retrieval tests.

Phase 4 — Observability

Implement CDN log collection, AI-agent user-agent analysis, origin-response monitoring, status-code dashboards, rendering comparisons, structured-data alerts, sitemap-freshness and canonical-consistency checks, deployment-to-cache validation, and AI referral and agentic-traffic reporting.

Phase 5 — Continuous testing

Test after CMS changes, front-end releases, CDN and WAF changes, URL migrations, international launches, structured-data changes, rendering-architecture changes, major product releases, and cache-policy changes.

12 · Checklist

Technical checklist

Crawlability

  • Important pages are publicly accessible
  • robots.txt does not block intended pages
  • XML sitemaps are available, current and canonical
  • Important pages have crawlable internal links
  • Navigation does not create crawl traps
  • Server logs are available for analysis

Indexability

  • No accidental noindex directives
  • Canonical URLs are present and correct
  • Canonicals agree with sitemaps and links
  • Retired URLs return appropriate status codes
  • Redirect chains are minimised
  • Soft 404s and duplicate variants are controlled

Rendering & JavaScript

  • Critical information exists in initial HTML
  • Important links work without JavaScript interaction
  • Server and browser renders agree
  • JavaScript failures do not empty the page
  • Essential content is not hidden behind tabs, clicks or scroll
  • Core rendering API calls are reliable
  • Rendering works across regions and devices

Machine readability

  • Semantic HTML with logical heading hierarchy
  • ARIA roles used appropriately
  • Structured data is valid and matches the page
  • Metadata is present in the server response
  • Canonicals are exposed consistently
  • Any AI discovery files stay synchronised

Infrastructure

  • CDN rules allow intended automated access
  • WAF rules do not issue accidental challenges
  • AI-agent requests are monitored
  • Cache invalidation follows deployments
  • Origin and edge responses are consistent
  • Rate limits do not cause avoidable failures

Measurement

  • Search crawling is monitored
  • AI-agent traffic and success rate are measured
  • AI-readable page coverage is measured
  • Source Visibility is tracked where available
  • AI referral traffic is separated from agentic
  • Technical changes correlate with visibility
13 · Summary

The final distinction

Technical SEO asks whether search engines can

  • Discover
  • Crawl
  • Render
  • Index
  • Rank
  • Present a website

Technical GEO asks whether AI systems can

  • Discover
  • Access
  • Parse
  • Retrieve
  • Extract
  • Reference
  • Use a website in generated answers
Technical GEO = technical SEO foundations + AI-agent accessibility + server-rendered, machine-readable pages + semantic structure + retrieval observability.
JavaScript is not the enemy. Essential information that is available only after JavaScript execution is the technical risk — the single thread that ties rendering, GEO and troubleshooting together.

Technical SEO and technical GEO are the implementation disciplines. Brand Visibility is the visibility and optimisation lens that connects technical access problems to AI-source visibility, agentic traffic and AI-driven business journeys. The two disciplines fix the web platform; the lens tells you where to look.
