Lesson 1 · The master mental models

Where work lives, and how it enters

Mental model

Workfront turns incoming work into organized, assigned, trackable outcomes. Start with how work flows through the system rather than memorizing menus.

Workfront answers five questions: what work arrived, what outcome is needed, what steps are required, who owns them, and what evidence shows progress.

1 · Workfront is a work funnel

Business need
Request or issue
Triage — should we do it?
Keep as issue / backlog
Convert to project
Tasks
Execution & updates
Reviews & approvals
Outcome delivered

A request or issue is work that has arrived but may not yet be fully planned. A project is a larger deliverable; tasks are the planned steps needed to complete it.

2 · Workfront is a filing cabinet

ObjectMental modelQuestion it answers
PortfolioFiling cabinetWhat broad business investments do we manage?
ProgramDrawerWhich projects support a common strategy?
ProjectFolderWhat major outcome are we producing?
TaskPlanned actionWhat specific work must happen?
Issue / requestIncoming noteWhat unexpected or newly requested work appeared?
DocumentSupporting materialWhat artifact supports the work?
Report / dashboardIndex or summaryWhat do we need to see across the work?

3 · Planned versus unplanned work

A project is the overall deliverable; a task is planned work required to achieve it; an issue or request is unplanned or newly submitted work that must be evaluated.

Project

Launch the summer campaign

The overall outcome being committed to.

Tasks

Write brief · create concepts · draft copy · legal review · publish

The planned steps inside the project.

Issue

Add an urgent French translation

Unplanned work that must be triaged against the plan.

4 · A project is a promise

“We will produce this outcome, using these people, within this timeframe, through these steps.” A credible project has a clear outcome, defined scope, tasks, owners, dates, dependencies, status, communication, and completion evidence.

5 · The project plan is a dependency graph

Write copy
Create design
→
Legal review
→
Publish

A task list tells you what exists. Dependencies tell you what can happen next. Durations, predecessors, task relationships, and assignments together shape the timeline.

6 · Workfront is shared memory

Workfront preserves what was requested and why, who owns each step, what changed, which files were used, what feedback was given, what was approved, and what remains blocked.

Key idea. Requests become projects; projects become tasks; tasks create outcomes; updates and approvals create trust; reports create visibility.
Practice

Classify each as project, task, issue/request, document, program, portfolio, approval, or report: launch a new website; write homepage copy; an urgent homepage change; approved brand guidelines; all digital marketing initiatives; website relaunch projects; legal sign-off; a view of overdue projects. (project; task; issue/request; document; portfolio; program; approval; report.)

6 · Execution and updates

A useful update answers four questions: what was completed, what is in progress, what is blocked or at risk, and what is needed from someone else.

Use an update for context and an issue when work must be assigned, tracked, and resolved. If the issue becomes part of the planned timeline, convert it into a task.

7 · Documents and approvals

Documents hold the work products and their history. A formal approval records who reviewed which version and whether it can move forward — Approve, Approve with changes, or Needs work.

8 · An unplanned request appears

Two days before launch, Product Marketing requests French social cutdowns. It first appears as an issue. The project manager weighs impact on scope, schedule, resources, legal review, and launch, then decides: decline, keep as issue, convert to task, or spin up its own project.

9 · Launch and closeout

The project is complete when assets are approved, published, and verified; open issues are resolved or transferred; actual effort is captured where required; status reflects completion; and the outcome is recorded.

One-minute explanation

Workfront receives work through requests, decides what deserves commitment, turns commitments into projects, breaks projects into tasks, connects tasks with dependencies, stores artifacts as documents, records progress through updates, controls quality through approvals, and provides visibility through reports and dashboards.

Practice

Model a product webinar as a project: landing page, speaker slides, email invitation, social promotion, registration tracking, legal review, event-day support, and a post-event report. Add dependencies, one unplanned issue, and a dashboard with in-progress, due-soon, pending-approval, open-issue, and completed views.

Lesson 3 · Workfront object relationships

Hierarchy tells you where; the network tells you how

Mental model

Workfront is both a hierarchy and a network. The hierarchy tells you where work lives; the network tells you who, what, and which decision are connected to it.

1 · The hierarchy

2 · The network

  • Tasks and issues → Updates
  • Projects → Reports and dashboards

A designer may be assigned to a task, be a member of a team, hold a job role, be mentioned in an update, and approve a document. These are relationships, not additional folders.

4 · Visibility is a separate model

Being connected to work does not grant the same access to it. Access level defines what a user can generally do; object permissions define what they can do on a specific object. Object permissions cannot exceed the access level.

Administrator policy
User access level
Permission on project
Inherited permission on child work
Actual ability to view or change data

5 · Relationship mistakes to avoid

  • Making every request a project.
  • Making every task a project.
  • Treating an issue as a task and hiding scope change.
  • Confusing a document with the work itself.
  • Using updates to track required work.
  • Assuming visibility means accountability.

6 · The five-question object test

#QuestionSignal
1What is the desired outcome?Substantial and multi-step → consider a project
2Is it part of the approved plan?Yes → task; no → issue or request
3Does someone need to perform an action?Yes → create trackable work
4Is there an artifact?Attach a document to the relevant work item
5Does the work need a formal decision?Use an approval, not only a comment
Core lesson. Objects are nouns, but relationships explain the system. A project without tasks is intention; a task without an owner is an obligation; a document without context is a file; an approval without a version is ambiguous.
Practice

Model a product webinar. Place it in a portfolio and program, define the project, add tasks and issues, identify documents, and name the project owner, task assignees, issue contact, reviewers, approvers, and dashboard reports.

Lesson 4 · Workfront as a workflow engine

How work moves from one state to the next

Mental model

Workfront is a state machine wired to a dependency graph: statuses show where work is, assignments show who must act, predecessors show what must happen first, approvals control quality gates, and notifications communicate change.

Once objects exist, the questions become: what state is the work in, who acts next, and what must be true before the next step begins.

1 · Status is the work item’s state

StateInterpretation
Not readyDo not begin yet
Ready / activeWork can proceed
Waiting / blockedAttention or dependency required
FinishedWork is complete
AbandonedWork will not continue

2 · Project status controls operating mode

Status modeUse it to…
PlanningBuild and refine tasks, dates, assignments, dependencies, and approvals
CurrentRun active work and notify the execution team
CompleteRecord that the defined outcome is finished
Planning = configure the machine. Current = run the machine. Complete = record the outcome.

3 · Assignments create responsibility

The project owner is accountable for the project; task assignees own specific execution; the approver owns the formal release decision.

Task exists
Person or team assigned
Work appears in the right queue
Person accepts or begins work
Work is completed

4 · Predecessors create order

A predecessor expresses “this task cannot begin until that task is complete.” Enforced predecessors create harder gates — not every relationship should be enforced.

5 · Approvals create quality gates

A comment provides feedback. An approval records a formal decision. Use an approval when a designated person must authorize the next stage.

→
Brand approval
→
Legal approval
→
Publish campaign

6 · Notifications are the nervous system

Notifications alert people to assignments, approvals, comments, updates, status changes, date changes, shared objects, and completed predecessors. Design them around required action, not every field change.

7 · Complete workflow example

Planning — build tasks, dates, predecessors, assignments, approvals
Current — team executes and updates statuses
Parallel work — copy and design proceed together
Approval — Brand approves; Legal requests changes
New version — team revises and resubmits
Publish — approved content goes live
Complete — outcome and evidence recorded

8 · Common workflow mistakes

  • Activating a project before the plan is stable.
  • Using dates instead of dependency logic.
  • Treating every delay as an issue.
  • Marking work complete without evidence.
  • Making approvals informal.
  • Designing noisy notifications.

9 · The five-part workflow test

#Question
1What state is the work in?
2Who acts next?
3What must happen first?
4What decision is required?
5Who needs to know?
Practice

Model a product-launch video requiring a brief, script, storyboard, filming, editing, internal review, legal review, and publication. Add one scope-change issue and decide whether it stays an issue or becomes a task.

Lesson 5 · Intake and requests

The front door for incoming work

Mental model

Intake turns an informal need into structured, reviewable work: Request → Information → Routing → Triage → Decision → Planned work.

Good intake keeps work from arriving through scattered email, chat, and meetings with no owner, priority, or business context. The queue is the front door; accepted work is managed elsewhere.

1 · Intake as a service desk

Topic groupDepartment or categoryWhat broad request type is this?
Queue topicSpecific serviceWhat exactly is requested?
Routing ruleDispatcherWho or what receives it?
RequestIntake ticketWhat need arrived?
TriageReview deskWhat should happen next?

2 · Request queues are front doors

Request Queue: Creative Services

│  ├─ Landing page
│  ├─ Email campaign
│  └─ Social media assets

Use one recognizable front door for a family of services, then organize related request types with topic groups and queue topics. Avoid both a single generic queue for everything and dozens of tiny queues.

3 · Request forms are intake schemas

A form guarantees a consistent minimum of information. It does not make the request good by itself — triage still evaluates feasibility, effort, priority, and ownership.

4 · Queue topics and routing rules

A queue topic classifies the request; a routing rule sends it to a team, user, job role, or destination project.

  • Landing page → Web Content team
  • Email campaign → Marketing Operations
  • Product video → Video Production
  • Presentation → Design team
Routing answers where the request lands. Assignment answers who owns the next action.

6 · Triage outcomes

OutcomeUse when…
Request informationEssential context is missing
DeclineWork is out of scope, duplicative, or infeasible
Keep as issueSmall or unplanned work needs tracking
Convert to taskWork belongs inside an existing project plan
Convert to projectWork has its own outcome, timeline, contributors, and approvals
Requested date ≠ committed date. The requester proposes a desired date; the delivery team evaluates capacity, complexity, priority, dependencies, approvals, and existing commitments before making a promise.

7 · Intake anti-patterns

  • One queue for everything.
  • Too many separate queues for closely related services.
  • Routing every request to one person.
  • Using form fields as the primary routing mechanism.
  • Accepting incomplete requests silently.
  • Converting every request into a project.

8 · Intake quality test

A complete request carries: outcome, audience, deliverable, required date, source material, approver, and success measure.

Practice

Design a Product Marketing Content queue for a feature launch. Add topic groups, queue topics, required form fields, routing, and triage outcomes. Then add a late request for a multilingual case-study video and decide whether to accept, split, defer, or create a separate project.

Proving the outcome can be delivered

Mental model

Planning proves that the requested outcome can be delivered with the available scope, time, effort, and people — not merely putting tasks on a calendar.

Templates standardize repeatable structures; durations and predecessors drive the timeline; Resource Planner handles higher-level capacity; Workload Balancer handles actual assignments.

8 · Check feasibility

Designer demand is 24 planned hours against 16 hours of available capacity — an 8-hour gap. Choices: add a designer, extend the schedule, reduce deliverables, reuse an asset, move another project, or accept visible delivery risk.

Scope, time, and capacity are connected. If the deadline cannot move, staffing or scope usually must.

  • Treating the requested date as a commitment.
  • Estimating only duration.
  • Assigning people before estimating work.
  • Building every project from scratch.
  • Adding predecessors before the plan is understood.
  • Confusing budget with schedule.
  • Ignoring actual hours.

An evidence-and-decision system

Mental model

Documents are the artifacts. Versions show change. Proofs focus review. Comments explain feedback. Approvals authorize progress.

2 · Document versus proof

A document is the stored file. A proof is the reviewable experience used for comments, markup, version comparison, and formal decisions. Not every document needs a proof.

3 · Versions preserve evolution

Upload a new version of an existing asset rather than creating disconnected files named “final,” “final-2,” and “approved-new.” Versions preserve what reviewers saw, what changed, and which revision was approved.

7 · Basic versus staged review workflows

Parallel review — Brand, Legal, and Product Marketing review the same proof independently. Sequential review — Creative review → Product Marketing review → Legal and Brand approval. Use parallel when participants can act independently; use sequential when one group’s decision depends on another’s.

10 · Common collaboration mistakes

  • Creating separate files for every revision.
  • Requesting feedback in a general update without identifying the version.
  • Treating every reviewer as an approver.
  • Approving an old version.
  • Using “Approve with changes” ambiguously.
  • Collecting unstructured comments after approval.
  • Mixing production feedback with business or legal decisions.

11 · Review-quality checklist

  • Correct asset uploaded to the right project or task.
  • Current version is clear and changes are identifiable.
  • Review instructions state what to examine and when.
  • Reviewers and approvers correctly assigned.
  • Parallel and sequential stages reflect actual decision logic.
  • The post-approval next step is known.

Mental model

Reports help people see. Dashboards help people focus. Fusion helps systems act — moving predictable handoffs while people keep judgment over acceptance, quality, scope, and approval.

9 · Worked example — automate content intake

Request created
Validate required fields
Missing → Needs Information → notify requester
Complete → classify request
Route by type — Web Content / Video Production / Creative Services
Human triage

After a human marks a request for conversion, Fusion can create a project from a template, copy request information, link the original request, notify the project owner, and update the requester. The acceptance decision stays human-controlled.

10 · External system examples

  • Workfront + Slack — notify a project channel when work becomes blocked.
  • Workfront + Jira — create an engineering issue and write its key back to Workfront.
  • Workfront + Salesforce — create or update a project when an opportunity reaches a stage.
  • Workfront + AEM — hand approved metadata to a publishing workflow and record the result.

11 · Automation needs observability & governance

For every important scenario, define its trigger, required data, conditions, success result, missing-data behavior, external-failure behavior, owner, failure record, and safe retry behavior. Make scenarios idempotent — check for an existing external ID and update rather than create, so a rerun never duplicates projects or records.

  • Consistent names for templates, queues, topics, reports, dashboards, and scenarios.
  • Define each status meaning once; avoid near-duplicate labels.
  • Require fields that support decisions — not every field.
  • Give every important object an owner.
  • Review and retire obsolete templates, reports, dashboards, topics, and integrations.
Final mental model

Workfront is a work operating system: requests are demand; triage is decision; projects are commitments; tasks are execution; dependencies are sequence; assignments are accountability; documents are artifacts; proofs are review spaces; approvals are authorization; reports are questions; dashboards are decision views; Fusion is automated handoff; governance is shared meaning.

Define the request queue and fields, triage outcomes, project phases, dependencies, review logic, daily and weekly dashboards, automation candidates, human-controlled decisions, and failure handling.
