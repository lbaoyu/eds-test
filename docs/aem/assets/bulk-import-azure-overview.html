Move SharePoint assets into AEM Assets through Azure.

How AEM’s Bulk Import uses Azure Blob Storage as a staging area, and why that’s the cleanest route for content that lives in SharePoint today.

The route

Three hops: SharePoint, Azure, AEM Assets

AEM’s Bulk Import collects files from cloud storage, not from collaboration sites. It can’t read SharePoint directly. Instead, the SharePoint content is copied once into a private Azure Blob Storage container, and Bulk Import pulls it from there into AEM Assets, folder structure and all.

Think of Azure as a loading dock. Content is copied there once, AEM collects it from there, and the dock is cleared when the move is done.

1 container plus one scoped, expiring access token. No personal sign-in.

Why Azure

Six reasons Azure is the cleanest staging area

Bulk Import supports several cloud sources. Azure Blob Storage is the most mature of them, and it fits naturally for organizations that already run on Microsoft 365.

Reason 1 · Continuity

Not tied to a person

AEM connects with a storage credential, not an employee’s sign-in. Password resets, MFA changes, and people changing roles don’t interrupt the import.

Reason 2 · Security

Scoped, expiring access

A shared access signature (SAS) token can be limited to one container, to read-only access, and to an end date. It can be cut off early if needed.

Reason 3 · Maturity

Adobe’s recommended route

Adobe recommends Azure or S3 for large and scheduled imports. Both Bulk Import interfaces support it: Admin view (Tools › Assets › Bulk Import) and the newer Assets view.

Reason 4 · Scale

Built for volume

No per-copy size caps or personal storage quotas. Very large files are fine, and any batch can be re-run safely.

Reason 5 · Transfer

Cloud-to-cloud copy

Files move directly from the container into AEM’s cloud storage. Nothing passes through a laptop or a browser upload.

Reason 6 · Control

Easy to inspect, easy to remove

IT can browse exactly what’s staged with Azure’s own tools before anything is imported. Once the migration is signed off, the container is deleted.

Key concepts

The eight terms you’ll hear

These terms come up in every conversation about this route. The examples use the sample company Meridian from the folder structure guide.

Storage account

Your organization’s Azure storage resource. It’s created in a region you choose and billed to your Azure subscription.

e.g. meridianmigration
Container

A private space inside the storage account that holds the staged files. A single container for the whole migration is typical.

e.g. aem-migration
Folders

Azure doesn’t have real folders. The path in each file’s name acts as one, and AEM turns those paths into real folders.

e.g. campaigns/2026/hero.jpg
SAS token

A signed, time-limited key that grants only the permissions it lists, such as read and list on one container. You paste it into AEM, and it stops working when it expires or is revoked.

read + list · expires after the migration
Source folder

The folder inside the container that an import reads. Everything below it is imported. The source folder name itself doesn’t carry over.

e.g. wave01/
Target folder

The AEM folder that receives the import. The subfolders below the source folder are recreated underneath it.

e.g. /content/dam/meridian
Import configuration

Saved settings in AEM: which container and source folder, where files go, filters, how to treat assets that already exist, and an optional schedule.

one per batch, reusable
Metadata file

A spreadsheet saved as CSV in the container. It gives AEM the title, tags, rights, and expiry for each asset as it lands.

built from SharePoint columns

How an import runs

What AEM does at each stage

Every import goes through the same stages, whether it’s 50 files or 50,000. The first two stages change nothing, which is why they always come before a real run.

01Check

Test the connection

AEM confirms it can reach the container and that the token is valid, not expired, and has the right permissions.

You seeA success or failure message.
02Dry run

Preview the import

AEM lists what it would import, flags assets that already exist, and reports problems. It doesn’t copy anything.

You seeCounts, conflicts, and warnings.
03Run

Copy into AEM

AEM copies each file into the target folder, recreating the folder structure and applying its naming rules on the way in.

You seeStatus moves from Processing to Succeeded.
04Process

Make assets usable

AEM creates thumbnails and renditions and applies folder profiles (default metadata, Smart Crops) and the metadata file. This step, not the copy, sets the overall pace.

You seePreviews appear and metadata fills in.
05Review

Confirm the result

The job history records who ran the import, when, the totals, and any files that failed, with logs. View Assets opens the target folder.

You seeA complete record for every run.
↻Controls

Stop, resume, schedule

A running import can be stopped. In Admin view, running it again resumes where it stopped. Imports can also be scheduled once, hourly, daily, or weekly to pick up new files.

You seeImports that are safe to repeat.

What happens to your content

What carries over, what changes, and what stays behind

Carried over

Structure, names, and originals

  1. 1
    Folder structureEverything below the source folder is recreated under the target folder.
  2. 2
    Original names as titlesFolder and file names as they appeared in SharePoint stay visible as titles, even when the underlying name is adjusted.
  3. 3
    Original files, untouchedThe original file is kept as-is. Previews, renditions, and crops are added alongside it.
Adjusted

Names and conflicts

  1. 1
    Folder names are normalizedLowercase, with spaces and special characters replaced by hyphens. “Autumn Rewards” becomes autumn-rewards.
  2. 2
    Special characters in file names are encodedFor example, % becomes %25. Renaming before the copy avoids this.
  3. 3
    Existing assets follow a rule you chooseSkip them, add the incoming file as a new version, or replace them (see below).

Stays behind in SharePoint Only files and folders move. Collaboration data doesn’t

SharePoint permissions, version history, comments, and check-out state don’t come across. In AEM, access follows the folder design, and history starts fresh. Column metadata comes across only through the metadata file.

Metadata & approval

How SharePoint columns become AEM metadata

Copying files carries only the files. Any extra columns a SharePoint library holds (campaign, market, usage rights, expiry) need a second path: export the library view to a spreadsheet, map each column to an AEM field, and save it as the import’s metadata file. AEM matches each row to its asset by the asset’s final location in AEM.

SharePoint column (example)Becomes in AEMWhy it matters
Title (text)TitleWhat people see in search and in connected apps. Local-language titles are fine
Description (text)DescriptionImproves search relevance and gives context to reuse
Campaign, Market (choice)TagsPowers search filters and smart collections. The tags must exist in AEM first
Usage rights (text)RightsTells reusers where an asset may and may not be used
Expiry date (date)Expiration dateAEM flags expired assets automatically
Approved (yes/no)Approval statusControls delivery. See the note below
Approval means delivery With Dynamic Media with OpenAPI, approved assets are deliverable

Only approved assets can be delivered, and an approved asset can be delivered publicly right away. Setting approval through the metadata file is effectively publishing. Reserve it for content that’s already cleared, such as brand logos. Everything else goes through normal review in AEM.

Safety net Metadata can always be applied later

The metadata file uses the same format as AEM’s standard metadata import. If any values don’t land during the import, the same file can be applied again afterward, so none of the mapping work is lost.

Security model

The token is the lock

The container stays private, and AEM gets in only with a token. Because the transfer runs cloud-to-cloud, that token, not a network rule, is what controls access.

01 · ContainerPrivate

No public access

Adobe asks for a private container that accepts only authorized requests. Nobody can browse or download the staged files without a valid credential.

02 · PermissionsRead + List

Least privilege, one container

The token only needs to list and read files. Add delete only if AEM should remove files after import. A token scoped to the container is more reliable than an account-wide one and limits exposure.

03 · LifetimeExpires

An end date built in

Set the token to expire shortly after the planned end of the migration. It can also be revoked early, by rotating the storage account key or removing the token’s access policy, which cuts off access immediately.

04 · NetworkToken-based

Network allow-lists aren’t supported

Bulk Import doesn’t support restricting the storage account to specific networks or IP addresses. Part of the transfer runs inside Azure’s own services, so access is controlled by the token, not the network.

05 · ResidencyYour region

Data stays where you put it

The storage account is created in the Azure region your policies require, on your own subscription. Storage and data-transfer charges apply for as long as the container exists.

06 · In AEMAdmins only

Restricted on the AEM side too

Only AEM administrators can create or run Bulk Import configurations. The token is stored in the configuration, not shared with users.

Good to know

Behaviors worth understanding upfront

  1. 1
    A one-way copy, not a syncChanges made in SharePoint after the copy don’t reach AEM unless they’re copied again and imported, either by re-running or on a schedule.
  2. 2
    Processing sets the paceAdobe doesn’t publish throughput figures. Generating previews and renditions takes longer than copying, so large libraries are imported in batches.
  3. 3
    Re-runs are safe by designWith Skip mode, running an import again only adds what’s missing, and a stopped run can pick up where it left off.
  1. 4
    One engine, two interfacesAdmin view and Assets view run the same Bulk Import engine. Both support Azure, health checks, dry runs, and schedules.
  2. 5
    Use a standard Blob storage accountAdobe’s documentation covers Azure Blob Storage. Data Lake accounts with a hierarchical namespace aren’t documented as supported.
  3. 6
    Folder design comes firstBulk Import reproduces whatever structure it finds. Arrange the container to match the target folder design before importing.
