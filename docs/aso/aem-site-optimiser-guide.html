Overview and trial

What is AEM Sites Optimizer?

Adobe Experience Manager (AEM) Sites Optimizer uses AI to find website issues, suggest fixes, and help teams apply approved changes through their existing publishing and development workflows.

Use this guide after the event to revisit the capabilities, check trial eligibility, and plan your first optimization cycle. You can read the examples without a product account. To explore your own site, confirm access with your Adobe administrator; your Adobe account team can help with eligibility, licensing, and next steps.

Start with a visitor need: fix a broken path to product information, make an important image accessible, or improve a slow landing page. Then review the recommendation, assign an owner, and check the result.

Trial at a glance

Start at no cost with three opportunity types and a defined monthly allowance.

Who it is for
Existing AEM Sites customers with a public, live production site using AEM Sites frontend delivery.
What it includes
Exactly three opportunity types: broken backlinks, Core Web Vitals, and missing alt text. Up to three identified issues per type each month.
Cost and duration
No cost. Usage-limited rather than time-limited.
Not included in trial eligibility
Login-protected sites, nonproduction environments, and headless delivery, where a separate frontend consumes AEM content.

Check the trial requirements and confirm your available actions and allowances in the application. Select the correct Adobe organization when signing in; follow domain-setup prompts if your site is not already available.

Trial terms are separate from paid-package entitlements. Documentation links are collected at the end of this guide.

The operating model

One loop. Different delivery routes.

The product workflow is Auto-identify → Auto-suggest → Auto-optimize. The available actions depend on the opportunity, your license, connected systems, and permissions.

  1. Auto-identify · Find the issue

    Inspect the affected pages and recent evidence. Decide what to address first.

  2. Auto-suggest · Review the fix

    Check the recommendation. Edit it where supported or ask the relevant specialist to review it.

  3. Auto-optimize · Apply the change

    Use the supported content or code workflow to apply the approved fix.

  4. Publish and verify · Check the site

    Complete publishing or the code release. Inspect the live change and check it again with fresh data.

Content route

Update the draft. Then publish.

Deploy to Author updates the authoring environment—not the live site. The author reviews and publishes through the content management system (CMS).

Author update ≠ live change
Code route

Review the code. Then release.

A Core Web Vitals fix can create a GitHub issue and pull request (PR): a proposed code change for review. Engineers test, merge, and release it.

Pull request ≠ live change

Some opportunity pages use “Deploy Optimization”; content workflows also document “Deploy to Author.” Follow the action and destination shown for the selected opportunity. Not every fix uses the same route.

Where supported, Sites Optimizer shows when a deployed change is confirmed live, has failed, or is detected again. Check the status for the specific opportunity and the release notes for availability. A live fix does not prove it caused a business improvement.

Two practical walkthroughs

Choose the content or code path

Use the content path for an image description. Use the engineering path for a code change. Both end with an approved live change and a check of the result.

Content walkthrough: fix missing alt text

Missing alt text identifies images needing review. Alt text is a text alternative used by screen readers. Review a small batch of informative images and describe what each communicates.

Fictional example · Luggage product page

Make purchase-critical information accessible

A luggage retailer shows the suitcase’s dimensions in a product image, but the page has no equivalent text specification. Sites Optimizer identifies missing alt text. The author reviews the image and supplies the size information shoppers need to assess the product.

Choose alt text in context. If equivalent dimensions are already available in adjacent text, avoid unnecessary repetition. Decorative images may correctly have empty alt text. Use the W3C image-alt decision tree to choose the right treatment.

  1. Inspect the image and page

    Open the missing alt text opportunity. Check the Page and Image, and read the surrounding content. Confirm the image is informative rather than decorative.

  2. Edit the recommendation

    Use the edit icon and review Target ALT text. Confirm each dimension against the labeled image and approved product specifications; never estimate size from appearance. Describe the image’s purpose concisely and avoid repeating nearby text unnecessarily.

  3. Apply the approved update to author

    Use the available deployment action. Check where it writes the change: page content, a source document, asset metadata, or another content model.

  4. Review, publish, and verify

    The author checks the page, runs Preflight if configured, and publishes. Check the live image’s alt text and reading experience, then rerun the relevant check.

Describe the purpose, not just the appearance.Linked images should name their action; complex diagrams may need a longer explanation. Check language versions and reused assets before changing shared metadata.

Engineering walkthrough: improve Largest Contentful Paint (LCP)

Core Web Vitals measure loading speed, responsiveness, and visual stability. Sites Optimizer uses Operational Telemetry—performance data from real visitors—and shows mobile and desktop evidence separately.

The documented analysis requires at least 1,000 page views per page. If no finding appears, check data coverage and freshness before concluding that the page has no issue.

Fictional example · Mobile landing page

Investigate slow loading of the main content

The mobile page’s p75 Largest Contentful Paint (LCP) is 3.4 seconds. The suggestion changes how the hero image loads. Review whether that fix fits this page—not every page.

p75 means the 75th percentile: 75% of recorded measurements are at or below the reported value. It is not an average.

  1. Inspect the metric and affected page

    Open the Core Web Vitals opportunity. Select the page and device, then inspect the loading, responsiveness, or layout-stability finding. Record the period and page-view count.

  2. Review the proposed code change

    Ask the engineer to check the patch, shared components, image selection, and loading behavior. Identify other pages that may be affected.

  3. Use the repository workflow

    Where enabled, Deploy Optimization creates a labeled GitHub issue and linked pull request. Review the actual diff and run the site’s existing checks before merge and release.

  4. Verify after release

    Confirm the intended version is live. Run controlled lab tests to catch immediate problems. Then compare new real-user measurements for the same page and device under similar traffic conditions.

A faster test is an early signal—not the final result.Lab tests run under controlled conditions. Field data comes from real visitors and needs enough new measurements after release. Check other pages that use the changed component.

Defined by your team

Add measures for verified fixes and business results

Verified fixes

Track approved issues confirmed resolved on the live page.

Define the check: Record how and when each fix was verified. This measure is not assumed to be built in.

Business outcomes

Measure CTA clicks, completed forms, or qualified leads in your existing analytics.

Define the count: Avoid duplicates. Adobe Analytics, Customer Journey Analytics (CJA), and testing tools require their own setup.

When attribution matters

Use a controlled comparison when it is appropriate

For a change that can be tested safely, randomly assign visitors to the original and updated experiences. Define the target outcome, traffic split, and guardrails before launch; then check statistical uncertainty and lead quality before calling a winner.

A change from 5.8% to 6.5% is +0.7 percentage points, but the difference alone does not prove causation. Predicted click-through rate is not a test result, and an opportunity does not automatically create an A/B test.

Keep denominators visible: a rate without its eligible sessions, page views, or completed actions is difficult to interpret. Record product activity separately from analytics outcomes and note meaningful changes to traffic, campaigns, or page content during the comparison period.

Simple operating cadence

Review the work at four gates

Review

Confirm the affected page, evidence, and proposed change.

Approve

Name the reviewer and resolve access or ownership gaps.

Deliver

Publish content or release code through the normal workflow.

Verify

Check the live result, remaining issues, and available fresh data.

Review pending and failed items regularly; do not expand the batch while changes remain unpublished or unverified.

Keep the record lightweight: site and opportunity, evidence reviewed, approved change, delivery owner, verification result, and next measurement date. If the fix is not live or the evidence is not yet sufficient, record the next action instead of claiming success.

Set the next review date based on when useful evidence will be available. Performance data may take time to accumulate; do not interpret a short observation window as proof of sustained improvement.
